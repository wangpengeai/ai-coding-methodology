# SDD + DDD + TDD 判定与门禁（规格治理）

> 三方法论的组合关系：**SDD 管「先写什么」**（规格变更先于实现变更），**DDD 管「逻辑放哪」**（领域边界、资产与语言），**TDD 管「怎么实现」**（红-绿-重构）。
> 本技能是规格资产的治理者与校验者：判定矩阵、门禁规则引用、快速通道与台账；执行流程（怎么做）归 workflow 插件，本技能不编排实现流程。规则、证据契约、模板与校验器的**唯一事实源**是共享内核（本插件 `core/` 目录）（经其 `manifest.json` 公开资产消费）。规则引用形如 `RULE-FLOW-002`（注册表：`registry.rules`）；过程证据按 `schema.gate-report` 输出（模板：`template.report.gate-report` / `template.report.delivery-report`）。

## 1 触发与偏好（opt-out 协议，RULE-OPT-001..004）

偏好机制**宿主无关**：先发现当前环境实际提供的项目级持久偏好机制（有则用，无则降级），不得猜路径或文件名。

- 记录字段：`scope`（all|sdd|ddd|ddd-strategic|tdd）、`mode`（persistent|current-task）、`reason`、`createdAt`、`createdBy`、`sourceMechanism`（见 `schema.opt-out`）；
- 写入后必须**读回验证**；验证失败只能应用当前任务豁免并如实报告「无法保证跨会话生效」；
- `current-task` 记录必须带任务标识且只在本任务生效，不得写入跨任务事实源；
- 包含关系：`all` 覆盖 sdd/ddd/tdd；`ddd` 覆盖 ddd-strategic；当前任务**显式启用**高于持久 opt-out；
- 恢复按 scope 幂等移除；仍被更广 scope 覆盖时必须报告「仍被抑制」；
- opt-out 只抑制主动触发，不是质量或安全保证。

## 2 适用性判定（RULE-FLOW-001，三项独立输出）

> 本矩阵由 workflow 元技能路由表在进入 plan-execution 前触发（内部接口-2）；项目无 `.sdd/` 体系时跳过。

分别判定并记录理由，禁止用一个全局开关整体启用/关闭：

- **SDD**：`required`（可观察行为/接口（IF 资产）/schema/架构边界/持久化格式/安全模型变化）｜`lightweight`（局部低风险行为变化，用最小变更草案）｜`exempt`（纯格式化、生成物刷新等不改变行为且可验证的工作——记录豁免理由）；
- **DDD**：`strategic`（业务能力/子域/上下文/跨上下文协作变化）｜`tactical`（既有上下文内的聚合/不变式/事件/服务变化）｜`not-applicable`（无领域语义变化）；
- **TDD**：`strict`（新增行为或可复现缺陷）｜`characterization-first`（遗留代码无测试覆盖，先锁定现状）｜`exempt`（测试不可行——必须按 RULE-TDD-005 记录授权与替代验证）。

DDD 投入等级偏好与 opt-out 分开保存；首次由用户选择（战略级/战术级），后续沿用并可临时覆盖。

## 3 前置条件与路由

| 方法论 | 前置条件 |
|---|---|
| SDD | 规格体系存在（需求基线/模块规格/变更流程） |
| DDD | 领域资产按等级存在（战略级=子域/上下文/地图/语言/追溯；战术级=聚合/事件/边界） |
| TDD | 测试设施可用（框架/运行命令/注入缝） |

缺口路由：

- **体系缺失** → 转交 `spec-backfill` 建立；
- **单次规格缺口** → 转交 `spec-writing` 补条目；
- **局部测试缺口** → 本任务内建测试骨架作为首步。

## 4 SDD 门禁（RULE-FLOW-002）

写实现前至少存在：规格落点、变更范围、可观察行为、验收条件、受影响接口清单与消费方处置/领域资产/风险。规格写作与登记按 `spec-writing` 执行。对外与模块间接口必须登记为 IF 资产（IF-域-n，经 `template.atomic.interface` + `template.atomic.interface-registry`），禁止只在分册正文定义接口（RULE-IF-001）。

架构、接口（IF 资产）、schema、领域边界、安全模型变化必须先修正式规格；普通局部变化可先登记最小变更草案（`template.atomic.minimal-change-draft`），完成前必须定稿。

接口条目达到 `active` 即冻结基线（operations + errorSemantics + 已登记工件哈希）；冻结后多任务可按契约并行开发，收口门禁重跑漂移证据比对，漂移未吸收不得宣称完成（RULE-IF-005）。

## 5 受控快速通道（RULE-FAST-001..004）

仅适用于：生产事故、紧急安全修复、高未知性探索性原型。

1. **编码前最小记录**：触发原因/范围/当前行为或问题/行为与验收假设/风险/计划验证/正式定稿触发点/接口影响声明（触碰接口时：受影响 IF-n 与消费方影响）；
2. 事故与安全修复**先写最小复现测试**；现实上无法做到必须记录原因与替代验证；
3. 允许在最小记录与最低验证后部署，但必须创建 **follow-up deadline**（负责人/到期时间/待补规格/待补测试/待补追溯），并持久记录到可被后续任务发现的位置；
4. **超期未定稿**：状态维持 `temporary-mitigation`，阻塞后续非紧急变更；台账写入失败时保持该状态并补录；
5. 探索性原型默认不得进入生产路径；保留前必须先完成正式规格、追溯与完整验证。

快速通道不是无限期「事后补文档」豁免。

## 6 DDD 门禁（RULE-DDD-001..004）

按判定等级经 DDD 模板组（`schema.ddd-assets` + `templates/ddd/` 全部模板，见 manifest）产出资产；战略级必含子域、上下文、Context Map、上下游与契约所有权、统一语言、事件风暴或替代证据、热点、领域追溯；战术级必给聚合边界影响结论与失败语义影响结论。N/A 必须附理由；既有资产未变化记录「已检查、无变化」。不得将 DDD 等同于任何固定目录分层。

## 7 TDD 门禁（RULE-TDD-001..005）

> TDD 执行纪律（红-绿-重构怎么操作）由 workflow 插件的 `tdd` skill 承载；本技能保留 RULE-TDD 的规则 ID 与证据留存校验职责（RED/GREEN 证据是否存在于 `内部治理状态`）。

## 8 完成门禁（RULE-FLOW-003/004）

完成门禁以 `/gate` 命令为唯一聚合入口（内部规则-3），本节不再重复定义。

## 9 输出契约

每个任务结束时输出交付报告（`template.report.delivery-report`）：触发原因、三项适用性结论与理由、偏好命中、前置与缺口、路由、变更条目、领域资产变化、TDD 证据、接口证据（受影响 IF-n/消费方处置/漂移结果）、校验结果、确认点、豁免、未验证项、剩余风险、最终状态。

## 10 红线（无豁免）

- 未完成适用性判定不开始实现；
- 无最小规格记录不写实现（快速通道也必须先留最小记录）；
- 不带证据宣称通过、完成或持久化成功；
- 不把超期未收敛的缓解状态当作完成；
- 不复制共享内核的规则或 schema 定义。
