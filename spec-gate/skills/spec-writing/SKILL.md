# Spec Writing：单次规格变更的写作权威

> 前提：权威规格体系已存在。体系缺失时转交 `spec-backfill`；流程启用与门禁由 `sdd-ddd-tdd` 负责。
> 本技能是规格语言与原子 schema 的语义维护者；条目结构、编号与模板的**唯一事实源**是共享内核（本插件 `core/` 目录，原 `sdd-methodology-core`）（经其 `manifest.json` 公开资产消费），本文件不复制任何 schema 定义。
> **写者权限≠实现批准**（内部接口-6）：加载本技能只获得规格/ADR 的落盘写作权，不构成对任何已定位修复的实施批准——不得借规格写作绕过所属任务的计划链（plan-writing→plan-review→plan-execution），把已决定的改动写成规格不使其合法；正常上游需求与设计的规格先行写作不受影响（写作是顺序问题，批准是权限问题）。

## 1 写作四步流程

### ① 确认与定位

确认体系存在，然后按变更性质定位落点：

| 变更性质 | 落点 |
|---|---|
| 新功能 | 需求基线（FR/NFR 登记）+ 模块分册 R |
| 模块内行为/边界 | 模块分册规格层（R/契约/D/T/边界/验收） |
| 接口（对外/模块间）/公共契约/依赖方向/数据 schema | IF 资产条目（`template.atomic.interface`）+ 接口注册表同步（`template.atomic.interface-registry`）+ 受影响分册；必要时 ADR |
| 跨模块时序 | 全局时序唯一主编号 G-T + 相关分册「细化 G-Tn」（多目标细化与 [G-Tn] 引用合法，见纪律 3 主编号口径） |
| 技术选型变更 | 技术约束基线 + ADR |
| 领域概念/术语 | 术语表 + 代码/规格/测试三消费面同步义务 |
| 受检清单收窄/排除裁决 | suite.json 顶层 `exemptions[]`（{path,reason,ref}）+ 在场条目 `documents[].note`——登记面随清单自解释，不外置台账（2026-09-20 使用反馈三批） |

### ② 选模板

按定位结果经共享内核（本插件 `core/`）manifest 读取对应原子模板（assetId 前缀 `template.atomic.`，完整清单以 manifest 为准）：
需求（requirements / module-requirement）、接口（interface / interface-registry；external-contract 已弃用，见 manifest deprecationMappings）、决策（design-decision + adr + adr-registry）、
时序（module-sequence / global-sequence）、边界（boundaries）、验收（acceptance-trace）、
术语与假设（glossary / assumptions）、未决项（open-items）、评审处置（review-disposition）、
变更影响与草案（change-impact / minimal-change-draft）。

### ③ 写作（七条纪律）

1. **规定性语气**：写「本模块必须/禁止…」；「代码目前…」只归注记层。
2. **量化与可操作锚点**：数值给上/下限，时机给可判定标准；禁止模糊表述。
3. **追溯完整**：R 标注 [FR-x]；验收标注 [R-x]；全局时序只允许唯一 G-T 主编号，模块条目只能写「细化 G-Tn」（RULE-SPEC-003）。主编号口径（2026-09-20 使用反馈三批语义澄清）：「细化 G-Tn」短语与 `[G-Tn]` 方括号引用是**引用**不计主编号——模块分册细化多个 G-T 条目合法；裸文本出现第二个 G-T 编号即「另起主编号」阻断；G-T 总表类文档（documentType global-sequence / traceability-matrix）豁免唯一性（罗列全部编号是其本职）。
4. **每需求至少一验收**：R 与验收同步编写，双向可查（RULE-SPEC-001）。
5. **决策必带备选**：D/ADR 无备选与否决理由 = 未完成的决策记录；ADR 字段以 `schema.adr` 与 RULE-内部决策-001 为准，不得缺项。
6. **验收方式如实**：自动化/人工冒烟/构建期检查/审查清单分清，不得把手测包装成自动化。
7. **先读代码再盘问**：对实现现状的任何技术盘问（接口、数据流、边界）之前，必须先读取相关代码并引用 file:line；禁止凭记忆或推测描述现状。

### ④ 自检与校验

提交前运行共享内核校验器（套件模式〔按 `内部治理状态`〕或文档声明模式）并逐项核对：

- 追溯闭合（FR→R→验收），无断链、无重复编号；
- 无未解析占位符；未决内容必须是结构化 `OPEN-n`——**禁止自由文本 TODO/TBD**（RULE-内部未决-001），blocking 未决项不得定稿（RULE-内部未决-002）；
- 规定性层无实现噪音（RULE-SPEC-004）；
- 跟踪边界与引用（内部接口-21）：不嵌随机器变化的活状态，引用运行态工件须可复核（本机审计指针须有可复现命令或冻结历史之一兜底）；
- 编号/结构变更 → 全部引用处同步，否则追溯断链。

## 2 规格与代码冲突裁决

**禁止直接假定任一方正确。** 先分类：

- 规格正确、实现偏离 → 同批回改代码，或登记紧急修订；
- 代码正确、规格过时 → 发起规格修订变更让规格追上代码，必要时补 ADR；
- 无法当场裁决 → 登记结构化未决项（含负责人与收敛触发），不定稿。

上线压力不构成让规格永久失真的理由；偏差必须留痕（RULE-FLOW-002）。

## 3 大型变更草案

跨多模块/探索性强的变更：先在受影响分册规格层新增 `[草案]` 小节。

- 编码前至少要有最小变更草案（范围/可观察行为/验收条件/定稿触发点）；
- 草案期间实验实现可在工作分支迭代，但**实验实现不等于已批准规格**；
- 合入以定稿为前置；定稿前追溯与验收必须稳定；
- 实验推翻设计时先回改草案再继续正式实现。

## 4 评审意见修订

收到评审意见：先分类（缺失/矛盾/精度/追溯/结构）→ 用评审处置表逐条记录处置（接受/修改/拒绝+理由）→
共性问题升格为模板或规则级修订 → 回归自检与校验器。

## 5 红线（无豁免）

- 不合入无验收的需求条目；
- 不在分册正文私自定义模块间接口绕过 IF 资产（RULE-IF-001）；接口变更必须覆盖全部已登记消费方处置（RULE-IF-002）；
- 不带未解析占位符或自由 TODO 定稿；
- 不复用已退役的 ADR/规则编号；
- 不复制共享内核的 schema 定义到本技能或项目文档；
- 不把偶然实现、已知缺陷或猜测升格为规定性规格。
