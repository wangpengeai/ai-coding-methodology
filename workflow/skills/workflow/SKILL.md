# workflow 元技能

任何开发任务开始时，第一个动作是查路由表——先于读代码、先于澄清提问、先于凭记忆选流程。路由表是全工作流体系唯一的场景判定入口（B-M1-1）：用户的当前状态必须经本表命中一个入口 skill，本插件内不存在也不允许存在第二个判定源。

使用纪律：

- 每次会话开始（含 clear/compact 之后）、每个任务到来、每次场景切换，都先重查路由表再行动；场景切换（如评审中发现缺陷）必须回到本表重新判定，不得在当前 skill 内顺手改道。
- 命中即进入对应入口 skill 并遵循其正文；本技能只判定与路由，不执行任何流程步骤。
- 命中行须机械声明：查表命中后，按当轮【workflow 任务租约】行给出的命令运行 `routing-declare.mjs <命中skill名> --lease <本轮leaseId> --task-id <任务号>`（任务号为域前缀形态 `<域码>-<序号>`，如 `内部任务-1`；**新任务**可直接照抄租约行/deny 文案内联的建议号（恰单域时自动给出）；**延续本任务**沿用原任务号重声明（同号幂等覆盖，勿照抄新建议号换号）；多域仓先 `--suggest-task-id` 按域描述判域；旧 `TASK-` 系形态不再接受）完成声明——本项目 Bash/Edit/Write 需持当前会话租约（Bash 整闸拦截，仅豁免单条严格解析的声明命令；Edit/Write 按文件归属仓键控），声明后本 prompt 内放行（下一条用户消息自动轮换）；宿主只读工具（Read/Glob/Grep 等）不经此闸，不受影响。声明是「查表已执行」的可验证凭据，口头复述不算。项目 skill 必载集合存在时，声明须逐项追加 `--project-skill <name>` ack（内部决策-070；缺失拒声明，见路由表命中行）。
- 宿主强制模式（如 plan 模式）期间：宿主模式优先，在模式内继续当前工作，路由判定挂起、不得在模式内强行改道去入口 skill；退出模式即视为场景切换，必须回本表重新判定。宿主 plan 模式的获批（ExitPlanMode 批准）只代表用户同意方案内容，不替代插件质量门——先经 plan-writing 落盘 docs/plans/、过 plan-review（或用户显式豁免并记录理由），才可命中「计划已批准」行。宿主模式内已完成的评审类勘察不视为插件口径评审：任务主体语义含审查（用户请求审查/审计）时，退出模式后须在修复执行前或收尾时以 code-review 对同一对象补一轮标准评审（三维 + specialist + ≥80 协议），或在计划中显式豁免并记录理由。

## 路由表

| 用户状态 | 路由到 | 显式触发条件 |
|---|---|---|
| 提出新想法/新产品方向，无 spec | `idea-review` | 提出仓库/方法论/产品层面的新方向，无 spec 且尚无「值得做」裁决——判定以状态为准，意图动词（想做/要不要做/评估一下/希望/打算/提议再做）仅为示例 |
| 任务已明确，方案未定 | `brainstorming` | 有明确对象与验收标准但无设计决策；属新方向的须已持 idea-review「值得做」结论，否则回上一行 |
| 有设计决策，要落成计划 | `plan-writing` | 用户说"出计划/写方案"或 brainstorming 批准门通过 |
| 计划已存在，动手前 | `plan-review` | 计划文档存在且未经评审；plan-writing 的强制出口 |
| 计划已批准 | `plan-execution` | 计划已批准且经 plan-review 通过（含宿主计划追认档）或用户显式豁免并记录豁免理由（声明 --exempt 时必须同时给出逐字引文、--exempt-scope plan\|review 与 --exempt-src user\|preauthorized；review scope 的计划须含 `豁免引文：` 行；豁免须针对计划流程本身明确表态，对结果目标的指令不构成流程豁免——内部规则-12；误声明退役用 --exempt-revoke + 撤销原话 + 已评审计划）——唯一进入实现的路径 |
| 报 bug/异常/回归 | `root-cause-debugging` | 互斥规则 1：此场景禁用 plan-execution，根因未找到不得提修复 |
| 用户请求审查/审计既有代码 | `code-review` | 用户要求审查/评审/审计既有代码（非助手完成声称，与上一行可区分）——无完成声称可验，免 verification 前置，评审对象按 code-review 三态判定；评审发现的缺陷回本表走正常调试/修复链（承接行= root-cause-debugging 接收问题反馈模式，内部规则-9） |
| 请求生产就绪评估，或 PR/候选版本已存在，要推进 CI、发布、部署、观测、验收或回滚闭环 | `production-change` | 已有可识别的 commit/PR/release/change 对象，且当前无正在发生的 bug/异常/回归（出现失败信号时由上方 root-cause-debugging 行优先命中；内部决策-009） |
| 用户显式要求接入或运行团队 AI 治理（模型策略/审批/租约/agent 评测/治理报告） | `team-governance` | 用户显式表达治理操作意图（接入/策略/审批/租约/评测/报告关键词）；插件未安装时输出可行动安装指引，普通开发路由不变（内部决策-012） |
| 代码已写完，声称完成 | `verification` → `code-review` | 互斥规则 2：verification 证据未运行，code-review 不得开始 |
| 分支收尾 | `branch-finishing` | 测试全绿 + 评审通过 |
| 周期节点 | `retro`/`health`/`learnings`/`architecture-evolve`/`external-radar` | 用户显式触发或 workflow 定期提醒 |
| 项目已立项算法迭代，或用户显式声明算法迭代/实验调优/bad case 处置意图 | `algo-loop` | 项目根存在 .algo/project.json（内部接口-22 激活锚），或用户显式声明算法迭代/实验调优/bad case 处置意图，且无进行中获批准计划（计划优先走 plan-execution 行）；与 Scout 模式同命中时本行优先（纪律档压探索档）；插件未安装时输出可行动安装指引（可选安装，内部决策-046） |
| 用户显式声明科研问题/假设检验/预注册意图（产出对外有效结论或实验证据） | `research-hypothesis` | 显式科研假设/检验/预注册意图且无进行中获批准计划（计划优先走 plan-execution 行）；与算法迭代行分界＝目的判据：改进实现/产品指标→算法迭代行，产出对外有效结论/实验证据→本行，两可时向用户澄清不得猜；与 Scout 三行同命中时本行优先（纪律档压探索档）；插件未安装时输出可行动安装指引（可选安装，内部决策-047） |
| 用户显式声明 CS 实验设计意图（消融/基准/种子对照/运行序） | `experiment-design` | 显式实验设计意图且无进行中获批准计划（计划优先走 plan-execution 行）；与研究假设行同命中（假设检验＋实验设计复合意图）时研究假设行优先——研究环从问题与判据进入，实验设计是其下游承接；与算法迭代行分界＝目的判据（同研究假设行，两可澄清不猜）；与 Scout 三行同命中时本行优先（纪律档压探索档）；插件未安装时输出可行动安装指引（可选安装，内部决策-047） |
| 需要开启、续期、毕业、放弃或迁移探路模式（Scout 生命周期管理） | `scout` | 用户明确表达模式开关/续期/毕业/放弃/恢复/迁移意图，或 SessionStart 注入提示到期检查点/事务待恢复/v2 声明待迁移（内部接口-9/12），或任务呈探索性/一次性交付特征（agent 提示、由用户确认 mode 与 expiry 后开启；scout 不替用户决定到期日，内部决策-008） |
| 项目处于有效 explore 模式，未命中上述行（兜底） | `spike-run` | 项目根有效 mode=explore（内部接口-9 v3 读取）且未命中其余 15 行；优先级低（内部决策-008 拆行） |
| 项目处于有效 disposable 模式，未命中上述行（兜底） | `disposable-build` | 项目根有效 mode=disposable（内部接口-9 v3 读取）且未命中其余 15 行；优先级低（内部决策-008 拆行） |

两条互斥规则（表内引用处在此展开）：

- **互斥规则 1（调试禁执行）**：调试场景（报 bug/异常/回归）禁用 plan-execution；根因未找到之前，不得提出任何修复方案。
- **互斥规则 2（验证先于评审）**：verification 的证据未实际运行之前，code-review 不得开始；"代码已写完"不等于"已验证"。

表外 skill 的进入方式：`code-discipline`、`tdd`、`doc-discipline` 由所属场景的入口 skill（plan-execution 等）按需引用，`writing-skills` 用于维护技能本身——它们不是场景入口，不参与用户状态的行命中判定。

表外声明保留名 `ad-hoc`（两道，2026-10-16 内部任务-116/内部未决-128 方案 B/内部决策-023 修正案 2）：非开发任务在 git 仓目录内需要写操作而路由表无行可命中时，以保留名为声明名走同一声明命令——它是路由表外的显式绕行出口，闸照常放行，自察归因按保留名区分；不可用于开发任务（开发任务必须命中表中一行）。两道分工：`ad-hoc`＝**状态型操作**（配置外部工具、装机/发布、环境运维——零代码/配置对象变更）；`ad-hoc-deliverable`＝**制品型交付**（PPT/文档/图表等一次性交付物——产出可评审制品）。声明侧成员校验认三组：表内入口、跨插件衔接 skill（spec-writing/spec-backfill/sdd-ddd-tdd/gate——声明须凭 `--via <表内入口>` 标注来源路由行，入租约供审计；衔接 skill 不设路由行，路由表仍是唯一判定入口）与保留名（ad-hoc/ad-hoc-deliverable），其余名称一律拒绝并按三组列出候选（判定纪律的机械兜底，2026-10-10 内部任务-29 扩集）。完成留痕分两形：**状态型**（ad-hoc）＝verification 证据 + operation 凭据 + 操作记录（内部决策-023 操作链：授权引文/授权范围/验证判据/回滚/生效边界一张记录，recordRef 强制绑定操作记录文件）；**制品型**（ad-hoc-deliverable）＝verification 证据 + 类型匹配评审凭据（`--review-mode deliverable`，渲染验收/内容审实例，instances ≥1）+ operation 凭据 + 操作记录（内部决策-023 修正案 2 制品链三环，gate 加 `--deliverable-chain` 旗标，四因子校验：旗标/评审环形态/双环同引最新 verification/code-review 先于 operation 签发）。**判据须含可机检状态断言**（内部决策-027 probe 探针，签发验形态/gate 执行回读，防操作者自证），按风险分级——L1 本地可逆强制 ≥1 探针、免授权复核 warning、免两阶段报告；L2 不可逆/跨边界探针可选、授权引文恒经 gate warning 人在环复核（制品链评审环另恒现 RULE-GATE-DELIVREVIEW warning 供人在环复核）。制品型评审的成本收益判据（三收益因子：仓外受众/大生成面一次成型/多源引用装配；纯自用草稿免评）见 `内部设计记录`。开发任务不得套用任一形态（其余混链形态机械拒绝）。

## 全局规则

以下规则对本插件全部 skill 无差别生效：除「自查举一反三」条作用于任何自查、评审与调试活动、「评审轮次熔断」条作用于任何评审活动、「代理实例复用与再水化」条作用于任何委派派发活动、「OPEN 消费面义务」条作用于任务开工（路由声明完成后、开工前）、「阻塞停机协议」条作用于任何执行期任务（含未落盘的推进过程）外，其余各条作用于任何落盘文档（多面声明不带计数序号——内部决策-043 修正案 1，顺修旧前言计数字面量与实列条数的既有漂移；内部决策-049 增「开工前消费面」面向）：

- **禁止自由文本待办标记（内部接口-8）**：任何落盘文档禁止出现自由文本待办标记字面量。跨会话仍未决的事项，唯一合法形态是 spec-gate 的 OPEN-n 结构化未决项；写作中发现未决项，当场登记或移交，不得以标记形式散落在正文里。
- **规格落盘归属（内部接口-8）**：规格文档的落盘永远归 spec-gate（spec-writing）。本插件的任何 skill 不得写 `.sdd/` 目录下的任何文档；对话级设计决策、实现计划（`docs/plans/`）、learnings/retros 等轻量资产归本插件，不进 spec-gate 受检文档集（反向边界）。
- **跟踪边界与引用规范（内部接口-21）**：跟踪文档只承载共享契约、冻结历史与追加式登记册，不嵌随机器变化的活状态；结论须能在不接触本机运行态文件的情况下被复核；引用运行态工件限三分类（可复现命令/冻结历史/本机审计指针），本机审计指针须有前两类之一兜底。
- **长任务阶段复审（指针条）**：长任务（多任务、跨会话）在阶段性目标达成后必须复审实现漂移，不等收尾一次清算；义务全文唯一载体在 plan-execution「长任务阶段复审」节——本条只做指针，不转述判据（防双写漂移）。
- **过程资产与归档资产分界（内部决策-039）**：落盘文档分两类——过程文件（任务执行期内的工作记录：`docs/plans/*`（计划/评审/执行台账/证据/DEBUG REPORT）、任务简报、进度台账；读者是任务参与者，允许工作痕迹）与归档文件（跨任务跨会话的事实源：`specs/`、`.sdd/` 受检文档、权威台账、`docs/design-docs/`（设计回写与契约取证面）、README/仓库维护说明、经验记录；读者是未参与任务的接手者）。两条铁律：①过程文件保留入库作审计链，但**不是事实源**，其内容不得被引用为依据；②归档文件只接收**经移交动作**的内容（逐条登记 + 过程文件回写标注去向）。过程文件中未决项的收尾移交义务全文唯一载体在 branch-finishing——本条只做定义与指针，不转述判据。
- **自查举一反三（内部决策-043）**：任何自查、评审或调试活动中发现一处问题，收口前必须按同模式做同类扫描——grep 同形态、对照同一规则逐处核对、同依赖面复算；扫描所得逐条处置或写明排除理由，「只修发现的这一处」不构成收口。义务全文唯一载体在本条；各 skill 自查节只放指针、不转述判据（防双写漂移）。
- **OPEN 消费面义务（内部接口-8，内部决策-049）**：任何 skill 在路由声明完成后、开工前，按任务域检索 `内部规格`（或项目声明的权威台账）相关未决项并显式处置（软约束不阻断；范围限非 blocking 档，blocking 档另有硬闸）；处置留痕落既有过程文档（plan-writing 计划头部「未决项排查」小节、root-cause DEBUG REPORT「分类检索」字段、brainstorming 对话记录）。义务全文唯一载体在 内部接口-8 §7.1（消费面义务）——本条只做指针、不转述判据（防双写漂移，「自查举一反三」条同款先例）；机械承载＝routing-declare 声明成功输出 OPEN 检索提醒行（内部规则-21，learnings 检索 内部规则-7 同款形态）。
- **项目 skill 消费义务（内部决策-070/内部模块-1 内部规则-25/内部模块-8 内部规则-28）**：项目存在项目级 skill 时，写操作前必须加载被 `x-required-on-write: true` 声明的必载项（发现根＝当前宿主专属项目根＋`项目级技能`，宿主根优先；机制不写死任何 skill 名）；SessionStart 每会话注入项目 skill 索引与义务；`routing-declare` 对必载集合逐项要求 `--project-skill <name>` ack（入租约 `projectSkills[]` 与发号台账），routing-gate/write-guard 对缺 ack 的写拒绝；清单缺失/损坏按源扫描解析（仅源扫描失败 fail-open）。义务全文唯一载体在 内部决策-070/内部模块-8 内部规则-28——本条只做指针、不转述判据。

## 跨插件衔接

项目存在 `.sdd/` 体系（`内部治理状态` 存在）时，除路由表外还须遵守三个衔接点；项目未接入时按未接入处理，不报错：

- **进入执行前过判定矩阵（内部接口-2）**：计划进入 plan-execution 前，先过 spec-gate 的适用性判定矩阵，按判定结论（required/lightweight/exempt 等）确定规格义务；判定依据不足时按 lightweight 处理，不得静默升级。
- **完成声称前跑门禁**：任何"完成"的声称之前，先调用 spec-gate:gate skill（或用户键 `/spec-gate:gate`）跑聚合门禁——含规格校验、台账与交付报告核验；报告结论（通过/不通过 + 关键项）留存于交付记录。门禁未过，完成声称不成立（agent 可自服务调用 gate skill，不必等用户键入命令）。操作型任务（ad-hoc 类）按操作链形态跑门禁（`--operation-chain`），完成档 = verification + operation 凭据 + 操作记录；开发任务维持双凭据链不变。
- **设计决策沉淀（内部接口-6）**：brainstorming 批准门通过的设计决策，沉淀走 spec-gate 的 spec-writing（design_decision → ADR 流程）；本插件 skill 不自行落盘设计决策文档。

## 边界与禁止项
