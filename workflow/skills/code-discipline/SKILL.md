# code-discipline：编码纪律（执行期随行）

三条随行纪律：外科手术式修改（改哪里、改多少）、极简实现（写多少、写什么）与改动工具（用什么改）。凡动手改代码即生效。

## 适用场景

- 随行 skill，不是入口：不开场、不路由，跟随一切写代码的场合——计划执行中、测试循环中、缺陷修复中、评审返工中。
- 与 tdd 的分工：本 skill 管"改多少"与"用什么改"，tdd 管"怎么验证"。两者在执行期同时生效、互不替代。
- 原则归位：经典四原则拆散归属后，本 skill 只承载外科手术式修改、极简实现与改动工具纪律；"先想后写"在 brainstorming，目标驱动在 tdd。单源无副本，各 skill 正文互不重复。

## 流程：三条纪律

### 纪律一：外科手术式修改

只动必须动的，只清理自己造成的。总判定：**每一行改动都应能直接追溯到本次任务的要求。**

负向清单（出现即违规）：

- 顺手重构：因为"看着不顺眼"而改与本次任务无关的代码。
- 改无关注释与格式：重排别人的空行、改写别人的注释、统一引号或缩进风格。遵循所在文件的既有风格，哪怕你自己会换一种写法。
- 修没坏的东西：对能正常工作的代码做"改进"。
- 清理别人的孤儿：仓库里原有的死代码，提一句让用户知道即可，不删（除非用户要求）。

正向清单（出现即义务）：

- 你的改动让某个导入、变量、函数失去全部引用时，删除它——只清理自己造成的孤儿。
- 发现无关问题时，一句话报备（看到了什么、影响什么）；修不修由用户决定，不顺手修。

根因修复的例外说明：修缺陷时，在共享函数里加一处守卫优于在每个调用点各加一处，属于修复根因的正当范围，不算顺手重构——但仍以能覆盖根因的最小 diff 为准。

### 纪律二：极简实现

解决问题的最少代码，不写任何投机的部分。

负向清单（出现即违规）：

- 投机性抽象：为只用一次的代码建抽象层；重复还没有实际出现就抽公共函数。
- 未要求的灵活性：添加没人要的配置项、可选参数、"以后可能用得上"的开关。
- 为不可能场景写处理：为不会发生的输入或状态写防御代码。
- 超出要求的功能：没被要求的行为不做。

自检：

- 写完发现明显可以更短——重写。两百行若五十行就够，五十行才是对的。
- 自问："一位资深工程师会不会说这段过度复杂？"会，就简化。

注意：极简不等于偷工。边界之内该做的完整实现（正常路径与真实存在的边界情况）由计划与测试纪律保障；本 skill 砍掉的是任务边界之外的东西。

### 纪律三：改动工具

改的是源码就走编辑工具，不拿脚本当编辑器。总判定：**结构类改动一律使用 Edit/Write 逐文件落盘；机械批量替换走下方受控通道，不手写脚本。**

负向清单（出现即违规）：

- 脚本批量改写源码：用 python heredoc、sed、awk、重定向追加/覆盖等方式批量替换或生成源码文件。写错不报错——绕过工具侧的变更可见性与失败信号，是"改了但没人看见"的高危形态（2026-09-16 实测：脚本批量替换把 5 个文件改到不可编译）。
- 用脚本"顺手"修正实现期发现的单处缺陷（哪怕一个字符）：顺手改与批量改的可见性问题同构，同样禁止。
- 把需要语义判断的替换交给脚本：脚本只能做机械映射，任何需要读上下文才能判断的替换都属于编辑工具的活。

受控通道（2026-10-31 内部任务-261/内部决策-066 扩面、2026-11-02 内部任务-285/内部决策-066 修正案 1 增窄声明级别；硬规则 9 白名单条件全文见 内部决策-066 D2）：

- 受信写者工具：`workflow/scripts/mechanical-edit.mjs`（literal-only 批量替换；expectCount 必填、默认 dry-run、计数不符整体不写、写后读回、审计）与 `workflow/scripts/evidence-gen.mjs`（证据清单生成；dry-run 默认、schema 校验、自指排除、写后复核、审计）；既有版本折叠（bump）与生成物物化（materialize）写者的条件不变。
- 显式声明：`routing-declare --script-write '<理由≥8 字>'` 登记本轮脚本写仓意图（理由与审计入运行态 `wf-script-writes.jsonl`），写仓闸据此放行；声明不豁免租约/写面判定。
- **受检路径（git 跟踪）的脚本编辑须更窄声明**：`routing-declare --script-edit-code '<理由≥8 字>'`（理由与审计入 `wf-script-edits.jsonl`）——受检路径上 C2 就地编辑/C3 内联写 API/C4 heredoc 喂解释器只认该声明，通用 `--script-write` 不足；C1 重定向写受检路径**直接拒绝**（任何声明不放行，改用 Edit/Write 或受信写者）。受检判定为启发式，git 不可用时回落现行裁决（可能仍 deny）并记 degraded（不冒充 clean）。
- 仓外写（tmp、运行态目录、宿主数据目录）不受限。
- 其余脚本写**受跟踪仓内文件**仍禁止；未跟踪仓内临时产物应优先放 tmp/运行态目录。

自检：

- 动手前自问："这一步改的是结构还是纯文本映射？"结构 → 编辑工具。
- 已经用脚本改了 → 当场自报，并逐处读回核对（内容有误或不可核验时按编辑工具修正），不做形式性回滚重做。

## 与其他 skill 的接口

- tdd：分工声明——本 skill 管"改多少"与"用什么改"，tdd 管"怎么验证"；执行期并行生效，互不取代。
- code-review：评审的 diff 噪音检查项以本 skill 的负向清单为准——评审时逐条对照 diff，甄别顺手重构、无关格式改动与投机抽象。
- plan-execution：执行计划时的随行纪律；执行中想把改动扩到任务之外时，以本 skill 为裁决依据。
- verification：本 skill 不含任何完成前验证内容，完成判定归 verification。

## 边界与禁止项

- 不含任何测试与验证内容：怎么写测试、何时运行验证，归 tdd 与 verification。
- 不定义进入条件：凡修改代码即生效，与路由表无关。
- 不与完整性对立：极简是"不做多余的事"，不是"少做该做的事"。
