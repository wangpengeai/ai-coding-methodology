# code-review：代码评审（发起与接收）

本 skill 承载评审会话里交替出现的两个角色：**发起**（把 diff 交给独立评审者，汇集带证据的意见）与**接收**（对每条意见先验证再处置）。两角色合为一个 skill 的两章（内部决策-1）——同一场评审里既要向评审者提问，也要回答评审者，拆成两个入口会让同一流程两处进门。两条硬纪律贯穿全篇：**意见必带证据**（≥80 置信度协议），**处置必先验证**（验证而非盲从）。

## 适用场景

- 用户状态命中路由表"代码已写完，声称完成"行的后段：verification 的证据已实际运行，进入合并或完成声明之前的最后一道关口（互斥规则 2：证据未运行，本 skill 不得开始）。
- 用户状态命中路由表"用户请求审查/审计既有代码"行：用户点名审查既有代码（功能缺口、规范、一致性审计等），无完成声称可验——免 verification 前置，但受理时必须注明评审基线（见"评审对象与范围"全量模式），评审发现的缺陷按路由表走正常调试/修复链，不在本 skill 内顺手修（"直接修"射程见 内部决策-2 节首限定）。
- 两条进入路径的受理核验（互斥规则 2 的可执行形态，内部规则-10 凭据化）：完成声称路径——`.sdd/` 项目受理前必须实际读到当前任务的 **verification 凭据**（内部接口-11：`assurance/cli.mjs chain-verify --task-id` 通过，或在 `内部治理状态<taskId>/` 读到 verification receipt 且其 RevisionSet 与当前一致），并在评审报告引用其 receiptId；读不到或 revision 失配即拒绝受理、退回 verification，不接受口头"验证过了"。用户点名路径——免该前置，报告须注明评审基线（其凭据形态为 inspection-only，永不进入完成链）。宿主模式内的评审类勘察不构成上述任一路径的受理凭据（内部规则-8）。操作链任务（ad-hoc 零变更）无 code-review 凭据属合法完成形态（内部规则-11），受理核验对之不适用；制品链任务（ad-hoc-deliverable）的 operation 凭据与 deliverable 评审凭据并存属合法形态（内部决策-023 修正案 2 四因子：评审环 reviewMode=deliverable、双环同引、序正确、经 `--deliverable-chain` 声明），不计冒用；若发现开发任务目录出现 operation 凭据（冒用操作链/制品链逃评审），按缺陷走 root-cause-debugging 接收问题反馈模式——判定时以凭据 riskLevel 与 gate 探针执行结果为口径（内部决策-027：L1 须经 gate 状态断言全过方可免评审，L2 仍有授权引文人在环复核；无 riskLevel 的旧凭据按 legacy 授权复核呈现）。
- **凭据签发（内部规则-10）**：完成声称路径的评审收尾（意见清单闭环、CRITICAL 处置完毕）后签发 code-review 凭据：`assurance/cli.mjs issue-code-review --task-id <任务号> --verification <receiptId> --review-instances <n> --review-round <n> --review-provenance '<JSON数组>' --fix-review-mode <none|self|delta|full> [--fix-review-instances <n> --fix-review-provenance '<JSON数组>' --fix-review-reason "<理由>" --fix-review-base <base> --fix-review-diff-sha <sha>] --summary "<一句话结论>"`——`--review-instances` 必填（CLI 强制：三维并行=3、单实例=1，自述不构成凭据；2026-09-19 评审修复 H8：原命令缺该必填参，照抄必被 argparse 拒）；`--review-round` 缺省 1；**非 exempt/user-audit 形态 `--review-provenance` 必填**（内部任务-191：条目 `{role,instance,chain,state}`，`chain=task:<taskId>`，round=1 全 fresh，countable（fresh|reused）数=reviewInstances；`rehydrated` 只补位不计入；exempt/user-audit 禁带）；`--fix-review-mode` 必填，无代码修复用 `none`（其余四字段须空），有修复按 内部决策-4 传对应档位与 base/diff，且 `fixReviewInstances>0` 时须带 `--fix-review-provenance`（countable=fixReviewInstances，round=reviewRound+1）；长任务的阶段级评审凭据另带 `--stage <阶段名>` 与 `--review-mode three-dim|single-instance|user-audit`（单实例评审以 `--review-mode single-instance --review-instances 1` 诚实兑现，内部规则-13）；受理校验（verification 凭据同任务、同 revision）由 CLI 强制；评审修复改变了源码，则旧凭据失效，须回 verification 重跑后再签。2.0.0（无 provenance 字段）的存量凭据按 legacy 可读（gate 产 `RULE-GATE-REVIEWPROV-LEGACY` warning 人在环复核）；2.1.0 非豁免缺任一字段读侧判死。
- 修复返工后的复审：按「修复后的复审分级（内部决策-4）」执行——以 review baseline 的修复 delta 为范围，按 none/self/delta/full 定档；从既有意见清单出发做增量复审，聚焦"处置是否到位、修复是否引入新问题"，不从零重来。
- 与相邻 skill 的分界：plan-review 评尚未执行的**计划文档**，本 skill 评**已写成的代码**；verification 生产**证据**（命令与输出），本 skill 消费证据并评代码本身；root-cause-debugging 的 DEBUG REPORT 是否合格不归本 skill 判定，但修复产生的 diff 照常接受评审。
- 发起与接收的时序：一次评审会话内通常先走发起章拿到意见清单，再切接收章逐条处置；外部评审者（人类或机器）对同一段代码提意见时，直接进入接收章。

## 发起评审（流程上章）

### 评审对象与范围（三态，内部规则-8）

- **评审冻结点（C1/内部任务-193）**：首轮派发前冻结评审对象（工作树收敛、规格/哈希重登与回归绿，此后不再改文本）→ 签 verification → **一次性**派发三维；同一快照只派一波；派发后至回执前对象变更即快照失效，只能走一次复审，不得补派第二波。

- **态一：增量 diff（默认）**：git 未暂存改动 + 当前分支相对基线的改动（以 merge-base 为基准的完整 diff，含已提交与未提交部分）。diff 由本 skill 在会话内取证后**随派发提示词附上**——评审 agent 只读、其 Bash 限四命令白名单（git diff/status/log/show，2026-09-18 内部决策-028），派发附 diff 是默认义务（未附时 agent 可用白名单自取，内部规则-4）。
- **态二：点名范围全量评审**：用户指名目录/模块/一致性审计（有 git 但无增量 diff 也走此态，不是降级）。取证义务从 diff 改为**文件清单 + 基线说明**（评审对象的路径集合、commit/版本/状态说明）；三维并行、specialist 派发（按涉及面而非 diff 大小）、≥80 协议、checklist 照常生效；意见清单注明"全量评审"。
- **态三：无 git 降级**（内部验收-1 失效分支）：降级为点名文件的全量评审——调用方列出本次改动的文件清单，评审按文件逐一对照，并在意见清单里注明"降级评审"。
- **diff 噪音预检**：派发前把 diff 逐块对照 code-discipline 的负向清单——顺手重构、无关格式与注释改动、投机性抽象、未要求的灵活性，出现在 diff 里即先记一条意见（这类问题优先报：它们污染的是评审范围本身）。
- 派发附带的上下文要精确剪裁：任务要求（计划步骤或需求条目原文）、verification 已运行的证据摘要、评审维度说明。给评审者的是工作产物与要求，**不给会话历史**——评审者该对着代码说话，不该被实现者的思路带节奏。派发输入附计划设计决策/不变量清单，不含实现者叙事/会话历史（内部决策-069 D4）。内部任务-191/D8：派发提示词须携带实例链身份 `task:<taskId>`、`round` 与「不得复用其他任务评审上下文，非本链实例不计入独立性」边界；回执要求声明 `role/instance/chain/state`。

### 三维并行评审（code-reviewer agent）

- 同时派 **3 个 code-reviewer 只读实例**，各领一个维度（内部规则-4）：
  - **简洁性**：有没有用更少代码达成同一目标的写法；是否夹带未要求的结构（单实现抽象、投机配置项、为不可能场景写的处理）。
  - **正确性**：逻辑与边界是否真的对——条件分支、错误路径、极值输入、状态迁移的每一步。
  - **项目约定**：是否遵守仓库既有模式——先读项目约定文件（AGENTS/CLAUDE 类文件、贡献文档），再对照相邻特性的写法。
- 实例间互不感知、输出各自自洽；三份报告由发起方合并，同一位置同一问题的重复意见归并为一条，置信度取各实例中的最高值。
- 派发与汇总都走对话，不落中间产物；最终只有一份合并后的意见清单。意见必带三件套＝违反的要求或不变量＋证据＋0-100 置信度；补丁建议不作为修复依据（内部决策-069 D4）。

### specialist 派发

- 三维之外，按 diff 的实际涉及面从 `specialists/` 目录点名专职提示词并入派发：

| diff 涉及面 | 派发 |
|---|---|
| 新增/修改可测行为、测试文件 | `specialists/testing.md` |
| 输入处理、鉴权、加密、外部调用、命令/文件执行 | `specialists/security.md` |
| 循环、查询、批量数据、网络调用、渲染 | `specialists/performance.md` |
| 共享状态、锁、异步任务、缓存写、事务 | `specialists/concurrency.md` |
| 对外接口（端点、参数、返回结构、事件、命令行） | `specialists/api-contract.md` |
| 新增会失败的路径（I/O、网络、解析、外部服务） | `specialists/error-handling.md` |
| schema 变更、迁移脚本、批量写、数据回填 | `specialists/data-integrity.md` |
| 用户可见行为、配置、默认值、文档/示例涉及面 | `specialists/docs-consistency.md` |

- 派发判定从 diff 出发、不贪多：某专职面完全未被 diff 触及时不派该 specialist；8 个全部不涉及的极小 diff，只走三维并行加 checklist 即可。
- 各提示词文件自带触发范围、检查重点与输出要求，派发时整文件并入提示词，不摘抄改写。

### checklist 核对

- 对照本目录 `checklist.md` 过清单，两遍法：第一遍只过 **CRITICAL** 类（最高严重级优先），第二遍过 HIGH 与 NORMAL。
- 清单是下限不是上限：清单之外、diff 里真实存在的问题照报；清单内类别在本次 diff 无涉及时记"无发现"，不硬凑凑数。
- 清单条目要求 diff 外取证时（如枚举新值要追全部消费方），用只读工具真去追，不在 diff 内部猜。
- **语义回收核验（U6 / 内部决策-058 决策 5，2026-10-23 内部任务-219）**：评审对象含删除/替换/退役类变更时，逐项核对「扫描零命中 / 登记状态更新 / 证据指针」三件套（口径同 verification skill 同名节）；任一缺失按阻塞意见提出，不得只以「测试绿」放行。

### ≥80 置信度协议（内部规则-2）

- 一切将报告的意见必须带两项：**0-100 的置信度**与**证据引用**（file:line 加能定位的原文关键词，B-M5-4）。评分依据是"证据被亲自核过的程度"——读过具体代码并确认缺陷成立才给高分；模式高度可疑但未核证的，先去核证再评分。
- **置信度低于 80 的发现一律不报告**：先补证再评，补不上去就丢弃。低置信度意见进入清单只会稀释高价值发现、制造噪声与误信。
- 本协议对三维 agent、specialist、checklist 核对的全部产出生效；agent 与各提示词文件同步声明同一协议，口径唯一。
- 意见必带三件套＝违反的要求或不变量＋证据＋0-100 置信度；补丁建议不作为修复依据（内部决策-069 D4）。

### 修复处置启发式（内部决策-2）

本节仅适用于完成声称路径的评审返工——处置对自己刚写的 diff 的意见。用户点名路径产出的意见清单按适用场景节移交 skill 外处置：修复动作回路由表走正常调试/修复链（root-cause-debugging 接收问题反馈模式，内部规则-9），不在本节"直接修"射程内。

意见确认成立后，按风险二分处置：

- **显然正确且低风险 → 直接修，并附测试**：机械修复属于此类——清理本次改动造成的孤儿引用、补参数化、魔数改命名常量、修正与代码漂移的注释、补齐缺失的边界测试。修复动作与对应测试记入意见清单。
- **有歧义或高风险 → 提问，不擅动**：涉及安全设计、并发语义、删除用户可见功能、超过小阈值的结构性改动的意见，把问题与建议方案摆给用户裁决，不动手。
- 分界直觉：一位资深工程师会不会不加讨论直接改？会，就直接修；合理的人可能对修法有分歧，就提问。**严重级越高越倾向提问**——CRITICAL 类意见天然风险更大，机械感是错觉。

### 修复后的复审分级（内部决策-4）

- **首轮发现处置时序（C2/内部任务-193）**：首轮评审发现批量**一次改完**（禁逐条边审边改/探索性重派）→ 按 内部决策-4 对首轮处置 delta 做**一次** delta/full 复审（触行为契约文本/风险面即 full）→ 复审通过后签 receipt；仍阻塞按 内部规则-22 五因子评估（默认继续）与升级裁决，不硬熔断。

修复 diff 本身是新的未评审代码。以上一轮评审/阶段门记录的 base 提交为基线，统计修复 delta，按「语义/风险优先于尺寸」分四档：

| 档位 | 判定 | 复审动作 | 凭据字段 |
|---|---|---|---|
| none | 零代码修复（意见全部驳回或转 OPEN-n） | 无 diff 可审；照常收尾 | `none` / 0 / 理由、base、diffSha 均空 |
| self | 无语义变更的机械修复（注释/命名/格式/测试期望同步），不触及风险面 | 自检四问 + 全量回归；记录一句「为何无语义变更」 | `self` / 0 + 理由 + base/diffSha |
| delta | 可执行语义变更，≤8 源码/契约文件且 ≤200 行，且不触及风险面；delta 仅限单意见/单位置局部修复（不按尺寸升档；内部决策-069） | 1 个 fresh-context 实例只审修复 delta + 直接影响面；按需 specialist | `delta` / 1 + base/diffSha |
| full | >8 源码/契约文件或 >200 行，或触及任一风险面，或修复改变设计/范围/推翻原评审结论，或批次交互（≥2 意见/≥2 位置/跨 ≥2 文件；内部决策-069） | 3 个 fresh-context 实例三维并行审修复 delta + 交互面；按需 specialist | `full` / ≥3 + base/diffSha |

- 风险面（命中即 `full`，尺寸不设豁免）：鉴权/加密/凭据、并发/锁/事务、闸/钩子/租约/凭据链、公开接口/CLI/契约/schema、数据迁移/持久化、新增依赖、权限/ACL/平台分支、行为契约文本（`workflow/skills/**`、`specs/**`、AGENTS/README 契约段）的语义变更。
- 行口径：`git diff --numstat <base>` 的新增+删除行；计源码/配置与行为契约文本，不计测试/生成物/`docs/plans/`；未知扩展按源码计。未跟踪文件先 `git add -N` 或纳入基线提交，否则行数与 diff 哈希失真。
- 规模不是唯一判据：一行鉴权改动按 `full`，一百行注释同步按 `self`；`self` 与 `full` 同时看似成立时取 `full`。
- 复审是增量复审，不从零重来：实例拿原意见清单、修复 diff 与相关代码，逐条回答「处置是否到位、修复是否引入新问题」。
- 修复复审 delta/full 轮另有 fresh 回归实例职责（只核修复是否引入新问题/不变量是否成立，不确认自身建议；none/self 轮以 D1 记录与回归证据自证、不派实例；不计入 fixReviewInstances；同链复用实例只核上轮意见处置闭环，复用优先纪律不变；内部决策-069 D3）。
- 任何修复改了已验证代码 → 先回 verification 补证，再复审；复审通过后再签发 code-review 凭据。
- 凭据签发命令见「凭据签发」节；按档位传 `--fix-review-mode` 与对应字段；`none` 只用于零代码修复，机械小修不得记 `none`。
- 机器只校验声明形态；真实性由评审记录（`git diff --numstat` 与 `sha256` 输出）与 gate `reviewAudit` 人在环承载。receipt 字段名：`fixReviewMode`/`fixReviewInstances`/`fixReviewReason`/`fixReviewBase`/`fixReviewDiffSha`。

### 复审实例复用矩阵（内部任务-181）

- **superseded 台账（C3/内部任务-193）**：实例台账状态词表含 `superseded`（草案/作废实例：记基线、失效原因、是否发现有效）；superseded **不计入** `reviewInstances`/`fixReviewInstances`，也不写入 provenance `state`（枚举仍 fresh|reused|rehydrated）。

- 同一链（首轮对象标识；stage 另加 stage）第 2 轮起优先续聊首轮实例；fresh 仅约束首轮（例外：修复复审 delta/full 轮另有 fresh 回归实例职责，none/self 轮以 D1 记录自证不派实例；见 内部决策-5，不计入 fixReviewInstances）。每轮按当前修复 delta 重算档位，取 max(首轮档位, 当前要求)——例外：当前修复 delta 为 `none`（零代码修复）时按 `none` 收尾，不因首轮档位强制升级。`none`/`self` 0 实例；`delta` 复用原 1，缺额补 fresh 1；`full` 复用原全部 ≥3，缺额按缺失维度补 fresh 至 3，禁止把 3 个实例压成 1 个。复用/补发保持维度映射（简洁性/正确性/项目约定）。
- 原实例不可用三态与证据要求同 plan-review；新发原因入评审记录。
- **首轮实例台账**：首轮结束即记 `内部台账<任务号>.md`（列与状态词表见元技能全局规则「代理实例复用与再水化」，append-only）；台账属过程文件（内部决策-039），不得被引用为事实依据。
- **跨阶段复用**：同一链不同 stage 标识的评审实例可复用（如首轮与阶段评审同源），不必新派全量；复用/补发保持维度映射（简洁性/正确性/项目约定）。
- **再水化登记**：新会话/实例不可续而必须新发时，按元技能全局规则登记为「再水化（重建）」，不得写成复用；原实例不可用证据同矩阵既有三态。
- **换号不重置**：同一首轮对象标识换任务号续审，沿用原链轮次并须用户裁决引文；否则视为新链无效。
- 多轮链强制落 `内部评审记录<task>.md`（链行＋逐轮意见摘要，append-only）；首轮结束即落，第 2 轮只追加。
- `fixReviewBase`/`fixReviewDiffSha` 仍记当前修复 delta；内部规则-16 判据不变。
- 通道选择与复用步骤（内部任务-220）：修复复审第 2 轮起——①有桥接清单：先列清单取同链同维度可续实例，经**续聊入口**续聊复用（缺失维度才补 fresh，保持维度映射：简洁性/正确性/项目约定）；评审实例只用普通子代理通道，不得改用持久成员通道。②无桥接清单：按本矩阵复用或新发。③新发一律登记再水化/新链，reviewProvenance.state 如实写 fresh/reused/rehydrated（rehydrated 不计入 countable）。
- **实例链身份与 provenance（内部任务-191）**：code-review 实例链身份＝`task:<taskId>`（与 plan-review 的 `plan:<planPath>` 分属不同链；跨任务实例一律拒）；首轮三维实例须同链 fresh，第 2 轮起按矩阵复用（state=reused）；再水化/跨链补位**不计入** `reviewInstances`；`crossStage:true` 须带非空 note；receipt 2.1.0 写 `reviewRound`/`reviewProvenance`/`fixReviewProvenance`，2.0.0（无 provenance 字段）存量凭据 legacy 可读 + gate warning。
- 熔断判据见元技能全局规则「评审轮次熔断」，本 skill 不重述。

## 接收评审（流程下章）

### 修复设计决策与复审对象（内部决策-5，内部决策-069）

接收评审后、执行任何修复前，先产「修复设计决策」并落评审记录固定小节（病根为设计缺口→回 brainstorming、规格缺口/歧义→回 spec-writing 修复后由 plan-writing 重写计划；不在修复批次内打补丁）：

| 字段 | 内容 |
|---|---|
| 病根分类 | 逐条意见→实现缺陷/设计缺口/规格歧义/范围外 |
| 修复后不变量 | 可验收、可回指计划/spec 的行为契约 delta |
| 修复批次 | 哪些意见一起改及理由（跨文件/多位置批次须显式列出） |
| 设计缺口回退 | 设计决策缺口→回 brainstorming；规格缺口/歧义→回 spec-writing；修复后由 plan-writing 重写计划，修复批次不得消化 |

- 评审建议文本不得直接作为修复依据；修复方必须按不变量重新推导改法。
- delta/full 轮修复复审每轮至少 1 个 fresh 回归实例（只核修复是否引入新问题/不变量是否成立；同链复用实例只核上轮意见处置闭环）；none/self 轮以 D1 记录与回归证据自证、不派实例。fresh 回归实例不计入 fixReviewInstances（记录面逐轮留痕；机器凭据仍按 内部决策-4 档位形态，不改 receipt schema）。
- 批次 full 触发见 内部决策-4 档位表（批次交互：≥2 意见/≥2 位置/跨 ≥2 文件）；批次 full 与每轮 fresh 回归双向独立：批次 full 不替代 fresh 回归职责，fresh 回归实例也不替代批次 full 覆盖义务；delta 仅限单意见/单位置局部修复（不按尺寸升档）。
- 评审记录每轮逐条标注 fix-induced（附「新发现位置∩上轮修复 delta」证据）；缺失 D1 修复设计决策节或 fix-induced 标注的修复视为未完成，复审阻塞。
- 简化档：none 轮批次字段不适用；单条机械修复可在记录内一行式决策（病根分类＋不变量＋批次＝1）。

### 验证先于处置

- 每条意见在处置之前先过验证四问：意见指认的现象在代码里核实了吗（去读对应位置）；意见在这个代码库与技术栈上成立吗；照它修会不会破坏既有功能；提意见的一方掌握完整上下文吗。
- **禁止表演式认同**：不说"说得对""好意见""感谢指出"这类认同与致谢空话——技术回应替代社交回应：要么一句话复述技术要点后动手，要么给出驳回理由。动作本身就是回应，代码修了就是听见。
- 意见含不清楚的条目时，**全部问清再动手**：各条意见可能相互关联，半懂状态下实施其中一部分，等于朝错误方向实施全部。
- 无法验证的意见（缺环境、缺数据、缺上下文）直说验证不了、缺什么、打算怎么补；不装作验证过，也不因验证不了就默认成立。

### 意见处置闭环

每条意见三选一，处置结果连同理由记入意见清单（位置/意见/处置/理由四项俱全）：

1. **采纳并修**：验证成立 → 按上文修复处置启发式执行；修复改动了已验证代码时，回 verification 补证（见接口节）。
2. **驳回**：给出技术理由——引用代码、测试输出或上下文，证明意见不成立、或照修会引入回归、或违反项目约定。驳回是技术判断不是立场对抗；自己驳回后被证明错了，事实性承认一句并立即修，不长篇道歉、不辩护当初为何驳回。
3. **转 OPEN-n**：验证成立但当下不修（超出本次任务范围、依赖未决事项）→ 登记结构化未决项（内部接口-8），写明回头条件。"挂着不处置"没有这个选项。
- 评审发现举一反三：单条发现采纳后、收口前，按元技能全局规则「自查举一反三」执行同类扫描——扫描面含评审 diff 之外的同形态处（同一规则被其他文件/模块调用的位置）；义务全文唯一载体在元技能，本条只做指针、不转述判据。
- 驳回外部评审者的架构级意见前，先交用户裁决——跨立场的架构取舍不是评审双方能单方面了结的。

### 规格歧义判定（必填节，内部接口-4）

- 每条意见在**代码级处置之前**自问一次：**该意见是否指向规格文档本身的歧义？**——即意见成立的根源是需求或规格没写清（两种读法都合理、规格与代码语义冲突、规格未覆盖该场景），而不是代码写错了。
- 判定为**是**：停止代码级处置，走 spec-gate 的 spec-writing **歧义类回流**（内部接口-4）——规格先改（[草案] 机制），代码随后跟；回流条目以 OPEN-n 或 ledger 记录留痕，关闭前可追溯。
- 判定为**否**：按上文处置闭环走代码级闭环。
- 本判定是必填字段：意见清单收尾时必须含"规格歧义判定"栏（是/否 + 一句话依据）；结论为"否"也必须显式记录——漏填视为无回流，但走查验收会检查该字段的存在性。
- **代码级意见不得处置规格文档本身**（内部规则-7）：对规格文档的评审意见归 spec-gate 的 review_disposition，本 skill 只判定与回流，不代改——同一意见不得两处处置（B-M5-2）。

### 会话收尾

- 意见清单全量处置完毕：每条都有"采纳并修（含修复与测试）/驳回（含技术理由）/OPEN-n（含编号）"三态之一，无悬空项；清单含规格歧义判定栏。
- 全部 CRITICAL 意见处置完毕（修复或驳回）之前，不得宣布评审通过，不得进入下游。
- 修复复审已完成且档位/实例数/base/diff 已记入凭据（`fixReviewMode`/`fixReviewInstances`/`fixReviewBase`/`fixReviewDiffSha`；`self` 带理由）；零代码修复记 `none`；receipt 2.1.0 的 `reviewRound`/`reviewProvenance`（及修复环 `fixReviewProvenance`）与评审记录/实例台账一致。
- 评审通过的要件：意见清单闭环 + verification 证据仍然有效——评审期间的修复改动了已验证的代码时，证据视为过期，回 verification 补证后再回来收尾。
- 跨会话仍未决的事项一律 OPEN-n，不留自由文本待办标记（内部接口-8）。
- 未决项移交指针（内部决策-039）：评审闭环后提醒——任务过程文件中登记的未决项须在分支收尾移交权威台账，义务全文唯一载体在 branch-finishing「未决项移交义务」，本条只做指针、不转述判据。
- **架构事实记录义务（内部决策-052/内部模块-20 内部规则-6）**：评审收尾时将架构级事实追加到被治理项目 `.context/architecture-feedback.jsonl`（义务全文唯一载体在 内部模块-20 内部规则-6；本 skill 只做指针、不转述判据）。

### 常见反合理化

| 念头 | 反驳 |
|---|---|
| "diff 不大，我自己过一遍就行" | 自己评审自己的实现，缺的正是外部视角；小 diff 的三维并行成本以分钟计，漏掉的问题以返工计。规模是效率判断，不是"要不要独立评审"的判断。 |
| "评审者说得挺有道理，照改就是" | 有道理不等于查过。先过验证四问；意见若根在规格歧义，照改会绕过规格一致性，必须走回流。 |
| "先改了再说，反正方向肯定对" | 每条意见先判定再动手是硬顺序；跳过判定的"快"，是用错误方向换的。 |
| "这条意见置信度不高，但宁多勿漏也报上" | 低于 80 的意见进了清单就是噪声：处置方要为它花验证成本，还会稀释真问题。补证到 80 以上再报。 |
| "驳回显得不客气，还是改了吧" | 驳回是技术判断，表演式认同才是失职。错的意见被照改，引入的是真回归。 |
| "修复就是照着意见改，不用再看" | 修复 diff 是新的未评审代码；按 内部决策-4 定档，self/delta/full 各有实例与证据义务，none 只用于零代码修复。 |
| "改动很小，记 none 省事" | none 只用于零代码修复；机械小修记 self 并附「为何无语义变更」理由，误记 none 即跳过复审。 |
| "修复很大但时间紧，先合再说" | full 档不得因时间压力降为 delta/self；可拆修复或交用户裁决，不得跳过复审。 |

## 与其他 skill 的接口

- learnings：正常收尾时提示记一条 learning（一句话 + 证据链接；允许显式说"无收获"跳过——跳过要出口，不沉默略过）。

- 上游：verification（互斥规则 2、T-M5-1）——其证据未实际运行时本 skill 不开始；评审期间修复使证据失效时，回 verification 补证，本 skill 等证据回到有效再收尾。
- 随行：code-discipline——diff 噪音预检以其负向清单为判定标准（顺手重构、无关格式改动、投机抽象、未要求的灵活性）；doc-discipline——「文档与注释同步性」检查项的判定口径以其七条款为准。
- 下游：branch-finishing——评审通过 + 测试全绿才进入分支收尾；本 skill 的通过结论是其一前置。
- agent：code-reviewer（只读，Bash 限 git diff/status/log/show 白名单——内部决策-028）——三维并行实例的载体；diff 由本 skill 取证后随派发附上（默认），派发未附时 agent 可用白名单自取工作区改动面。
- 跨插件（spec-gate）：歧义类回流走 spec-writing（内部接口-4，规格先改代码后跟）；未决意见登记 OPEN-n（内部接口-8）；规格文档本身的意见处置归 spec-gate 的 review_disposition（内部规则-7，单处置原则）；缺陷类回流（评审中发现规格**缺陷**而非歧义）经路由表回 root-cause-debugging 场景按其判定节处理，本 skill 不代行。
- 本 skill 只产出会话内意见清单与处置记录，不写 `.sdd/` 下任何文档。

## 边界与禁止项

- **无验证输出的代码不接受评审请求**（互斥规则 2）："代码已写完"不等于"已验证"；先 verification 后此处，路由表执行（T-M5-1）。
- **不评审计划**：计划文档的评审归 plan-review；本 skill 的对象是代码 diff，不给"计划该怎么写"的意见。
- **不处置规格文档**（B-M5-2、内部规则-7）：发现规格层问题只登记与回流，不代改、不双重处置。
- **置信度低于 80 的意见不报告**（内部规则-2）；报告的意见必带置信度与证据引用，缺任一项的意见不得进入清单（B-M5-4）。
- 修复以意见为单位走启发式，不做意见范围之外的顺手重构——改多少归 code-discipline 裁决。
- 修复复审不得省：`none` 只用于零代码修复；`self` 须证明无语义变更；`full` 不得因时间压力降为 `delta`/`self`；`fixReviewBase`/`fixReviewDiffSha` 缺失的修复复审不成立。
- 不维护跨会话评分看板或评审日志；跨会话未决的唯一合法形态是 OPEN-n。
