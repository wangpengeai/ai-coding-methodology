# branch-finishing：分支收尾（集成路径裁决与落地）

收尾是分支生命周期的最后一步：核对前置证据、复看相对基线的完整 diff、让用户拍板集成路径、落地并清理。本 skill 只做"怎么把已验收的工作合回去"，不做任何新的评审或实现——那是上游 skill 的事（内部规则-1）。

## 适用场景

- 路由表命中"分支收尾"行：测试全绿且 code-review 通过之后，用户说"合并/收尾/提 PR"时进入。
- 前提（内部验收-1）：项目用 git 分支承载开发；无 git 时降级为"目录快照 + 人工搬运"建议并向用户明说，不假装执行 git 操作。
- 收尾是链条终点（T-M6-1）：verification 与 code-review 未完成时，本 skill 的正确动作是拒绝开始并指回上游，不是"顺手补验收"。

## 流程

### 第 1 步：收尾前置核对

六项全过才继续，任一缺失即回上游，不在本 skill 内补救：

| 核对项 | 通过标准 | 缺失时去哪 |
|---|---|---|
| verification 证据 | 验证命令真实运行过（命令/退出码/输出摘要俱全）且结果全绿 | 回 verification |
| code-review | 评审已完成，问题清零或遗留项已记录为接受项 | 回 code-review |
| 交付报告 | `.sdd/` 项目存在当前任务的 delivery-final（gate receipt 链完整，内部决策-007） | 回 assurance gate/finalize |
| 计划步骤 | 有计划文档时步骤全部勾完；未勾项要么补完、要么明确砍掉并记录原因 | 回 plan-execution |
| 未决项移交 | 任务过程文件中的未决项（OPEN-n／计划内引用号）已移交到项目声明的权威台账（逐条登记 + 回写过程文件标注去向） | 在本分支内完成移交；项目未声明台账时先向用户确认去向 |
| 自察归属记录（内部决策-041） | 收尾前运行插件根 `scripts/incident-cli.mjs list`，「本任务归属待排查记录」（＝待排查面 ∩ 本任务/本会话归属；证据面 `probe-noise`/`replayable-rejection`/`mechanism-trace` 不计，内部决策-063 D4.2）逐条 triage 或 resolve 留痕（warning 级不阻断——未清零可收尾但须知情；批量收口可用 `triage/resolve --matching-excluded --older-than Nd --note`（仅用于超龄证据面归档，不用于清零本行待排查——本行逐条 triage/resolve 或按 `list --json` 的 `counts.pending` 定位）） | 回 root-cause-debugging 或 incident-cli 分诊 |

**未决项移交义务（内部决策-039，义务全文的唯一载体）**：任务过程文件（`docs/plans/*` 等）中登记的未决项，收尾时必须移交到**权威台账**——`.sdd/` 项目默认 `内部规格`；非 `.sdd/` 项目须在 仓库维护说明（或等价约定文件）设「权威台账」节声明各域台账；项目未声明时，收尾必须向用户确认未决项去向（建立台账或逐条呈报裁决），不得静默留在过程文件。**未移交即收尾不成立**——同本表其余核对行，缺失即回上游、不在本 skill 内补救。plan-execution 收尾与 code-review 会话收尾只做指针、不转述本段判据。

"测试全绿过"不等于"现在还全绿"：以最近一次真实运行且覆盖当前树（其后无未验证改动）为准。

### 第 2 步：基线核对（完整 diff 复看）

1. 确认基线分支：分支从哪分出来通常写在计划文档或分支名里；不确定就问用户确认——合错基线的撤销代价远高于一次确认。
2. 复看相对基线的全部改动：`git diff <base>...HEAD --stat` 看轮廓、`git log <base>..HEAD --oneline` 看提交序列、再通读完整 diff。
3. 复看是收尾人视角的自查，不是评审：查调试残留、临时文件、计划外的顺手改动、不该入库的本地配置——发现即在本分支内处理或移出。
4. 工作区若有未提交改动：先按第 5 步 commit 规范落成提交或明确排除，不带脏工作区做集成。

### 第 3 步：集成路径选择（用户拍板）

呈现三条路径与适用条件，等用户选择——集成决定是用户的，本 skill 不代选：

| 路径 | 适用条件 | 落地动作 |
|---|---|---|
| 本地 merge | 单人仓库或想保留分支上的提交结构 | 切回基线、merge 功能分支、在合并结果上重跑测试、通过后删功能分支 |
| squash 后 merge | 分支上多为过程性提交（试验、修补），主干历史要一条线 | 压成单个提交合入，消息概括"做了什么、为什么" |
| push + PR | 团队协作、需 CI 与他人评审 | push 分支、按仓库模板建 PR；工作区保留等 PR 反馈 |

执行纪律：

- 本地 merge/squash 后必须在合并结果上重跑测试；失败即停，分支与现场保持原样排查，不强行推进。
- push 被拒说明远端已前进：先查明差异再决定；未经用户明示不做强推。
- 删除分支仅在合并成功之后；丢弃整个分支的工作只响应用户的显式要求，且先确认工作区里没有仅存于此的未提交文件。

### 第 3.5 步：生产交付交接（内部规则-5，用户有生产意图时）

集成完成后、收尾结束前，若用户有发布/部署意图（或项目存在 delivery profile），输出结构化交接并可发起生产变更草稿——本 skill 只交接不推进（不等待 CI、不发布、不部署）：

- 交接内容：taskId、base/head SHA、PR refs（如有）、required checks、verification/code-review/gate receipt 引用、planned version（如有）、delivery profile 适用性。
- 发起草稿（可选，经用户确认）：
  ```bash
  node <spec-gate 安装根>/assurance/production.mjs --project-root <项目根> init --task-id <任务号> --profile <项目根>/内部治理状态
  ```
- 无生产意图时跳过本步，收尾照常结束。

### 第 4 步：可选清单

- CHANGELOG：项目已有 CHANGELOG 文件时，按其既有格式从 diff 提取用户可感知的变化补记；项目没有该文件不主动新建。
- VERSION/tag：项目自身走 semver 发布流程时，可选地提版本号或打 tag，跟随项目既有习惯；非必须步骤，本 skill 不代做发布、不裁决版本号。
- 工具链观察汇总：任务过程中发现的本插件体系/宿主/外部工具链自身缺陷（含未造成阻塞的——阻塞项靠决策门被迫上报，非阻塞项没有通道，正是本项要补的环），收尾时汇总呈报用户，按类分流可选登记——运行异常走 `incident-cli.mjs`（内部决策-019 通道）；插件行为缺陷经 spec-gate 流程登记 OPEN-n（本 skill 只指路，不直接写 specs/，B-M6-1）；可泛化的坑记 learnings 一句话（场景=工具链）；上游三方问题由用户裁决。无观察显式说明跳过，不硬凑。

### 第 5 步：commit 规范与 PR 描述要点

- commit：一个提交一个意图，消息写清"做什么、为什么"；squash 路径下过程性碎提交合并，不做无意义的美化。
- PR 描述五要点：改了什么（对 diff 的概括）、为什么改（动机/关联问题）、怎么验证的（测试命令与结果，引用 verification 证据）、评审状态（code-review 结论）、计划文档链接（如有）；仓库自有 PR 模板时以模板为准。

## 与其他 skill 的接口

- 上游：路由表顺序 verification → code-review → branch-finishing（互斥规则 2 保证验证先于评审，T-M6-1 保证收尾最后）；本 skill 进入前只核对上游产物，不重做。
- plan-execution：第 1 步"计划步骤全勾"消费它的执行状态，有未决项时回流补齐。
- learnings：收尾完成后提示记一条 learning（一句话，T-M6-2 约定）——有真实收获才记，允许"无收获"跳过，不编造。
- 随行：doc-discipline——收尾复看 diff 时，仓内文档与代码是否同一变更单元更新、注释是否仍与实现同步，以其七条款为判定口径（收尾的移交动作改的是归档文件，纪律适用）。
- 自察收口（内部决策-019/内部决策-041/内部决策-063）：收尾前运行插件根 `scripts/incident-cli.mjs list`（注入行给出可直接复制的绝对路径）；**本会话新增**的待排查自察异常须 resolve 或 triage 留痕后方可宣称收尾完成；**本任务归属残留**（历史遗留待排查记录；证据面按 内部决策-063 D4.2 分层排除、不属本行）按 内部决策-041 为 warning 级不阻断——未清零可收尾但须知情留痕（处置入口见第 1 步核对表第六行，终评处置：两态口径显式分立，防与新行冲突；证据面记录（含本 turn 新产生者）的观测出口＝`incident-cli list`/`digest`/retro `causeCounts`，超龄归档＝处置（30 天，不产数字），均不进 Stop 归属行）。

## 边界与禁止项

- 不做评审：diff 复看中发现实质问题（缺陷、设计疑问）时停止收尾、回 code-review 重开评审；本 skill 内不"顺手修"。
- VERSION 队列与跨分支评审看板不移植（内部决策-2）：版本排队自动裁决与多分支评审状态聚合是原工作流体系的特有闭环，多数项目用 semver tag 即可，本插件不重建；版本操作只跟随项目自身习惯。
- 不写 `.sdd/` 与 `docs/plans/`（B-M6-1 反向边界）：规格与计划文档落盘归 spec-gate；本 skill 只操作 git 与项目既有文件。
- 集成路径不代选：三路径的适用条件是建议，最终拍板永远在用户；宁可停下等确认，不替用户做单向门决定。
