# plan-review：计划四视角评审（plan-writing 的强制出口门）

评审对象是计划文档，不是代码。一份计划在进入实现之前，先在这里过四副眼镜：工程与 CEO/创始人两个默认视角串行执行，开发者体验与设计两个视角按需加深。结论只有两态：通过，路由表才放行 plan-execution；不通过，退回 plan-writing 修订。评审的产出是项目内评审记录与结构化未决项，不是口头意见，更不是外部日志。

## 适用场景

- 用户状态命中路由表"计划已存在，动手前"行：`docs/plans/` 下存在计划文档，且未经评审，或评审通过后被实质修订。
- 评审未通过后的重审：plan-writing 按评审记录修订完成，带着新版本回到本 skill；重审从既有记录出发，聚焦上一轮的阻塞项。plan-review 不通过后的修订，plan-writing 必须先产修复设计决策节（内部决策-069 D1）。
- 与 plan-writing 的分界：那边写计划，这边只评计划；与 code-review 的分界：那边评已写的代码，这边评尚未执行的文档。
- 进入条件由 workflow 路由表唯一判定，本 skill 不自定义；计划尚未成文（只有口头方案或设计文档）不受理，退回 plan-writing 先落计划。

## 评审总则

- **评审对象是计划**：全部意见指向计划文本——目标、范围、步骤、验收——不评实现，实现还没有发生。评判基准沿用 plan-writing 的读者画像：一位称职但不了解本仓库、不了解本领域的执行者，只读自己那一步能否照做。
- **结论两态，无中间态**：
  - **通过**：两默认视角的阻塞项清零，计划可交执行；此后路由表命中"计划已批准"行。
  - **不通过**：任一已执行视角存在未清零的阻塞项；计划退回 plan-writing 修订，修订后重新评审。不接受"带病通过"，也不接受"先通过、意见以后再说"。
- **评审记录落盘**（内部决策-2）：结论与全部问题清单写入 `docs/plans/<plan>-review.md`（`<plan>` 与计划文档同名）；不建跨会话评分看板。跨会话仍未决的意见，唯一合法形态是 spec-gate 的 OPEN-n（内部接口-8），不留自由文本待办标记。结论行格式（`结论：通过` / `结论：不通过`，独占一行、顶格无列表前缀——`^结论` 行首锚定）是机器门禁的读取契约（内部规则-8）——routing-declare 声明 plan-execution 前按此行校验已评审凭据，格式改动即门禁失效，不得增删该行形态。**多轮评审命名（2026-10-10 内部任务-29）**：重审通过档建议落 canonical `<plan>-review.md` 名，历史轮改名 `<plan>-review-roundN.md` 归档；机器凭据按内容匹配同 stem `-review*.md` 全序列（内部规则-10 扩）——归档轮与 canonical 并存不失效，有效凭据＝与当前计划哈希匹配的那一份（哈希绑定、单有效），故归档形态不影响门禁，canonical 落位只是惯例推荐。
- **默认顺序串行，禁止并行**（B-M3-1）：视角一（工程）→ 视角二（CEO）依次执行。理由：工程结论决定 CEO 关注点——范围被判过大时，CEO 的范围模式门要换姿态重审；架构已被锁定后，CEO 不再重复技术辩论。并行四视角既浪费又会漏检。视角三（开发者体验）、视角四（设计）为可选加深，在两默认视角之后按需执行。
- **通过即快照**：通过之后计划再有实质修订，原评审记录作废、必须重审。"只改了两行不用重评"被本规则显式拒绝——重评可从既有记录出发，但不能免掉。
- **意见必须可定位**：每条意见指向计划内的具体位置并引用原文关键词；涉及代码现状的断言（"这个文件里已经有 X"）以 code-explorer 的勘察证据为准，不凭印象下结论。
- **评审的默认立场是怀疑而非盖章**：评审阶段发现一个问题的成本以分钟计，执行阶段发现同一个问题以返工计。找不到问题不丢人，放过问题才是失职；某检查块确实零发现，写"无发现"收尾，不硬凑。

四视角总览：

| 视角 | 姿态 | 默认性 | 启用条件 | 核心产出 |
|---|---|---|---|---|
| 一：工程 | 工程经理：锁范围、锁架构、核测试 | 默认必执行 | 无条件 | 范围判定、架构与测试问题清单 |
| 二：CEO/创始人 | 创始人：零静默失败、盯范围与账本 | 默认必执行 | 无条件 | Prime Directives 结论、范围模式判定 |
| 三：开发者体验 | 接口设计者：为下游使用者着想 | 可选加深 | 计划含对外接口面，经用户确认 | 接口易用性问题清单 |
| 四：设计 | 设计师：为最终用户着想 | 可选加深 | 计划含界面/文案/交互流，经用户确认 | 用户可见性问题清单 |

## 评审实例模式（内部规则-16）

评审实例的独立性按计划改动面分档，不让「自评还是独立评」由会话上下文决定。**实例**指由宿主子代理能力派出的 fresh-context 执行体；**sidecar** 指 `docs/plans/<plan>-review.md` 凭据文件。两者不得混称。

**实例分档阈值**：实现类计划统计步骤数、文件级清单文件数、新模块数；超过 8 步、超过 8 文件或超过 2 个新模块（任一）即超阈值。步骤数只数带编号/标题的步骤标题（裸「## 步骤」伞标题不计；数字标题仅在无步骤标题时回退计数）。文件数只数「文件清单」节内的文件令牌——节在下一个同级/更高级标题或任何步骤/任务标题处结束；根级文件与任意扩展名均计，版本号/短缩写由形态排除。新模块数按表格动作单元格/列表项前缀的动作词（新建/新增/创建/添加/new/add）与非测试/文档路径计。无文件清单时以实现词（`skill`/`hook`）或非验收行代码路径/代码围栏兜底判实现类，并直接按超阈值处理；纯文档计划（含验收命令里的代码路径）不触发。机器计数是下限：人工嗅探可因清单遗漏**上调**档位，不得下调。文件/新模块口径与第 3 步「改动面嗅探」一致，但该节只判范围异味；实例义务以本节阈值为准（另含步骤数）。

| reviewMode | reviewInstances | reviewReason | 低阈值 | 超阈值 |
|---|---|---|---|---|
| independent | ≥2 | 必填（两视角各由哪个实例执行） | 允许 | 允许 |
| mixed | =1 | 必填（哪个视角独立） | 允许 | 拒绝 |
| self | =0 | 必填（自评范围与理由） | 允许 | 拒绝 |
| ratified | =0 | 必填（宿主批准时间/范围/来源） | 允许 | 拒绝 |

- 真值表口径：`independent ≥2`、`mixed =1`、`self =0`、`ratified =0`；表中未列组合一律拒绝。
- 超阈值实现类计划只接受 `independent`（工程/CEO 各由首轮 fresh-context 实例执行，可串行，符合 B-M3-1）或拆小；宿主无子代理能力时由用户显式 `--exempt "<逐字引文>" --exempt-scope plan|review --exempt-src user|preauthorized` 留痕，不得以 `self`/`mixed` 冒充。
- 派发失败/超时：重试一次；仍失败按宿主无能力处置（拆小或用户豁免），不得主会话自评后改写 `independent`。
- `ratified` 仅低阈值追认档使用；超阈值计划不适用追认档（内部决策-020 修正案 1）。
- `reviewInstances` 只数 countable 槽位（state=fresh|reused；首轮全 fresh、第 2 轮起复用计 reused；round=1 时不允许 reused）；事实核查 code-explorer、可选 devex/design 实例不计入。
- 评审记录正文必须写「改动面嗅探：X 步 / Y 文件 / Z 新模块 → 超阈值/未超阈值」与每视角执行实例标识（子代理名/ID 或「主会话自评」）；sidecar 的 `reviewInstances` 须与记录一致。
- 残余面：实例是否真实存在、`self` 是否真的无语义变更、`ratified` 的宿主批准，机器不能证明；机器只校验声明形态，评审记录与用户抽查承载真实性。
- **v3 凭据（内部任务-191）**：独立/mixed 的 sidecar 必须 `schemaVersion: 3` 并带 `reviewRound`（1..999；与文件名 `-review-roundN.md` 的 N 一致；round>1 须存在前轮归档）与 `reviewProvenance`（单行 JSON 数组：条目 `{role,instance,chain,state,note?}`；`chain` 必须等于 `plan:<planPath>`，跨任务一律拒；`state∈fresh|reused|rehydrated`；role/instance 同凭据唯一；round=1 须全 fresh；`crossStage` 仅 code-review receipt 使用，本 sidecar 不接受）；`reviewInstances` 只数 countable 槽位（fresh|reused），**rehydrated 补位不计入**。v2 仅 self/ratified 历史可读，独立/mixed 判拒并给出迁移文案。

### 评审实例派发提示词契约（v3，内部任务-191）

派发每个评审实例时，派发提示词须含统一固定块（缺项即不得声明该实例计入独立性）：

- 评审对象：`planPath`、当前 `planSha256`（LF 口径）、`taskId`；
- 链身份：`plan:<planPath>`（plan-review）/`task:<taskId>`（code-review），并写明「本实例属于该链，不得复用其他任务的评审上下文」；
- 视角与轮次：工程/CEO（或三维维度）与 `round`（与 sidecar/receipt 一致，round>1 时附前轮档路径）；
- 边界：显式写「非本链实例、跨任务再水化实例不得计入独立性计数」；
- 回执：实例回执须声明 `role/instance/chain/state`（复用/再水化写 `state` 与轮次；plan sidecar 不写 `crossStage`），收口时据此写 sidecar 的 `reviewProvenance` 并登记实例台账。

### 复审实例复用矩阵（内部任务-181）

- **superseded 台账（C3/内部任务-193）**：实例台账状态词表含 `superseded`（草案/作废实例：记基线、失效原因、是否发现有效）；superseded **不计入** `reviewInstances`/`fixReviewInstances`，也不写入 provenance `state`（枚举仍 fresh|reused|rehydrated）。

- 同一链（planPath）第 2 轮起优先续聊首轮实例；fresh-context 仅约束首轮。每轮按当前计划重算阈值，所需模式取 max(首轮模式, 当前要求)：`independent` 复用首轮全部实例（≥2）；`mixed` 复用 1；当前要求升为 mixed 而首轮为 `self`/`ratified`（0 实例）时补发 1 个 fresh；当前要求升为 independent 而首轮不足 2 时补发 fresh 至 ≥2。复用/补发必须保持原视角映射（工程/CEO 不得互换）。
- `self`/`ratified` 首轮无独立实例，不适用复用。
- 原实例不可用三态（不存在/已终止不可续/上下文丢失）；新发前须记录一次续聊尝试（宿主错误/实例不可达）与原实例 ID，上下文丢失须有宿主错误或用户裁决引文；新发原因入评审记录。
- **首轮实例台账**：首轮结束即记 `内部台账<任务号>.md`（列与状态词表见元技能全局规则「代理实例复用与再水化」，append-only），供第 2 轮复用与不可用三态判定；台账属过程文件（内部决策-039），不得被引用为事实依据。
- **跨阶段复用（仅 code-review 有 stage 维度）**：plan-review 链无 stage，按 planPath 链轮次复用即可；code-review 的 stage 属轮次链键，跨 stage 复用＝轮次链不同、实例链相同（`task:`），须在 receipt 的 reviewProvenance 登记 `crossStage`/note 与理由，复用/补发保持视角映射；事实核查/勘察类实例不计入 reviewInstances，不得顶替评审实例。
- **再水化登记**：新会话/实例不可续而必须新发时，按元技能全局规则登记为「再水化（重建）」，不得写成复用；原实例不可用证据按上述三态。
- **ratified 禁止**：同一 planPath 存在未闭合 blocking 评审记录时，不得以宿主追认档产出通过 sidecar。
- **换号不重置**：同一 planPath 改任务号续审，沿用原链轮次并须用户裁决引文；否则视为新链无效。
- 每轮落 `<plan>-review-roundN.md`（失败轮同样落，结论「不通过」），链行记锚点/轮次/上轮路径，append-only。
- 通道选择与复用步骤（内部任务-220）：第 2 轮起按序执行——①有适配层桥接清单时：先列清单取同链同角色可续实例，经**续聊入口**投递本轮计划与轮次（派发契约 v3 同前）；清单无该标识或投递返回不可续/未知才新发，失败原文入台账；评审实例只用普通子代理通道，不得改用持久成员通道。②无桥接清单时：按本矩阵复用原实例（可含持久成员通道）或按不可用三态新发。③新发一律按「再水化/新链」登记，不得以 fresh 冒充复用、也不得把复用写成 fresh。
- 熔断判据见元技能全局规则「评审轮次熔断」，本 skill 不重述。

## 宿主计划追认模式（内部决策-020）

宿主 plan 模式内经 ExitPlanMode 获用户批准的计划，不必重走四视角全流程，但也不经宿主批准直接放行——经本模式补一份机器可验的凭据，凭据形态与标准评审档同构。

- **入口条件**：宿主 plan 模式的 ExitPlanMode 已获用户批准（批准只代表用户同意方案内容，见 workflow 元技能红旗表），且批准的计划已按批准内容落盘 `docs/plans/`；缺任一项回标准流程（先 plan-writing 落盘，再四视角评审）。
- **单一有效 sidecar**：同一计划同时只允许一份有效 sidecar——追认档与标准评审档互斥，后出者作废先出者（与「通过即快照」同一语义）；追认通过后计划再有实质修订，追认档同样作废，重新追认或改走标准评审。多轮评审下并存的历史轮归档（`-review-roundN.md`）不构成第二有效凭据——有效凭据由当前计划哈希唯一锚定（内部规则-10 扩，2026-10-10 内部任务-29）。**适用范围**：追认档仅适用于低阈值计划；超阈值实现类计划不适用追认档（内部规则-16 / 内部决策-020 修正案 1），须独立实例或用户显式豁免。
- **核对范围只两项**——宿主批准已覆盖方案取舍，本模式不重复表态：
  1. **执行性**：任务可分阶段，阶段边界与交接物明确，每步有「验收：」行；
  2. **验收口径**：每步验收可机验（命令 + 期望输出或退出码）或含明确检查点，不留"运行测试确认通过"式不可判定验收。
  任一项不满足 → 不是补 sidecar 能救的缺陷，退回 plan-writing 修订后走标准评审。
- **产出**：标准 v2 sidecar（「输出格式」节模板原样），frontmatter 增一行 `ratify: host-plan` 标记来源，并写 `reviewMode: ratified`、`reviewInstances: 0`、`reviewReason: "<宿主批准时间/范围/来源>"`；正文记录追认依据与两项核对结论，结论行格式契约不变（`结论：通过` 独占一行）。`verifyReviewedPlan` 不校验 ratify 字段——追认档凭据与标准档同等效力（容忍性由 plan-review-binding 测试锁死）；机器只校验 `reviewMode=ratified` + 0 实例 + 非空理由。
- **豁免边界**：追认档跳过 内部规则-11 的受理核对阻塞项（用户裁决 2026-09-13，内部决策-020——宿主批准即用户裁决，不二次阻塞）；但 内部规则-11 的精神不豁免——追认计划若含实现类步骤，执行侧收尾的 code-review 与 learnings 沉淀义务不变，缺收尾审查或缺 learnings 沉淀的缺口不因追认消失。

## 流程

### 第 1 步：受理核对

- 确认评审对象：`docs/plans/` 下的具体计划文档，用户指名或路由表命中。
- 查同名评审记录：无记录 → 首次评审；记录为"通过"且计划未再改 → 告知已通过、按路由表流转，不重复评；记录为"不通过"或计划已实质修订 → 重新评审，新记录标注取代了哪份旧记录。
- 计划缺 frontmatter `specRefs`、步骤缺"验收："行（plan-writing 的格式契约）→ 直接记入视角一问题清单，评审照常进行，不因格式缺陷中止。
- 实现类计划（含代码或 skill 资产修改步骤）的收尾节缺 code-review 步骤，或缺「learnings 沉淀」步骤／该步骤**未排在 verification 之前**（即排在 verification 之后，或落在完成链后续步骤），且无豁免记录（内部规则-11）→ 直接记入视角一问题清单并**标阻塞**——计划缺收尾审查即允许执行以未评审 diff 宣称完成；learnings 后置或缺失则把「事后提醒」当成沉淀通道。纯文档计划的豁免须在计划内记录理由，无记录同样阻塞。
- 实现类长任务计划（步骤数或文件清单超阈值——阈值与「评审实例模式」节的实例分档同源，含多阶段结构）的收尾节仅安排单次评审、无阶段复审门，且无豁免记录（内部规则-13）→ 直接记入视角一问题清单并**标阻塞**——长任务缺阶段复审门即允许执行把大 diff 推到收尾一次评审（阶段偏差与局部缺陷混成一锅、返工面=整批）；阶段复审门的最低形态=计划中标明哪些阶段性目标达成后必须发起一次 code-review（可写进对应任务的验收行）。豁免口径同 内部规则-11（计划内显式记录理由，无记录同样阻塞）。
- **改动面嗅探与实例模式（内部规则-16）**：按「评审实例模式」节统计步骤/文件/新模块并写入评审记录；超阈值实现类计划必须按 `independent` 执行（工程/CEO 各一首轮 fresh-context 实例，可串行），否则直接记入视角一问题清单并**标阻塞**——不得以 `self`/`mixed`/`ratified` 通过；低阈值计划可自评，但 `reviewReason` 必填。
- **设计输入检查（内部规则-17）**：运行 `node workflow/scripts/check-plan-design-input.mjs <计划路径>` 并记录结果——**exit 0** 通过（结果写入评审记录「设计输入检查」行）；**exit 1** 将 violations 逐条记入视角一问题清单并**标阻塞**（缺节/缺角色/字段非法/证据不可定位；旧计划重审按同契约补记，证据不可回溯时以 self/waived 如实留痕）；**exit 2** 为工具错误、检查未完成——**不得进入通过结论**，修复后重跑。整体豁免与 waived/self 行须在评审记录中呈现给用户确认，未确认记阻塞。**宿主追认档不执行本项**（内部决策-020 边界；残余见 内部规则-17）。
- 例外：宿主追认档经「宿主计划追认模式」节进入，不受本核对（含 内部规则-11 阻塞项）阻塞——用户裁决 2026-09-13，内部决策-020；追认档自身只核执行性与验收口径两项，豁免边界见该节。追认档仅低阈值适用（内部规则-16 / 内部决策-020 修正案 1）。
- **多宿主适配检查（内部规则-18）**：运行 `node workflow/scripts/check-plan-host-impact.mjs <计划路径>` 并记录结果——**exit 0** 通过（结果写入评审记录「多宿主适配检查」行）；**exit 1** 将 violations 逐条记入视角一问题清单并**标阻塞**（缺节/空节/闭集外状态/行证据不可定位/豁免歧义/实现类误用整体豁免）；**exit 2** 为工具错误——**不得进入通过结论**，修复后重跑。整体豁免与负态理由须在评审记录中呈现给用户确认，未确认记阻塞。**宿主追认档不执行本项**（内部决策-020 边界）。
- **测试锚定检查（内部规则-19，内部决策-060）**：运行 `node workflow/scripts/check-plan-test-anchors.mjs <计划路径>` 并记录结果——**exit 0** 通过（结果写入评审记录「测试锚定检查」行）；**exit 1** 将 violations 逐条记入视角一问题清单并**标阻塞**（缺节/位置错/叙事行 invalid-anchor/派生引用悬空/实现类整体豁免）；**exit 2** 为工具错误——**不得进入通过结论**，修复后重跑。**引入批过渡**：checker 尚未落盘（由本批计划引入）时以静态核对第 9 条契约与计划节形态替代并记录，checker 落盘后同批补跑，不得静默跳过。整体豁免理由须在评审记录中呈现给用户确认，未确认记阻塞。**宿主追认档不执行本项**（内部决策-020 边界）。
- **批次级基线收缩联动（内部规则-20）**：核对本批变更触及模块的未锚 A 行是否**同批收缩**（结构化锚或 waiver），或计划内显式登记「本批不收缩」理由与回头条件；无收缩且无显式理由 → 记入视角一问题清单非阻塞项（不放行静默库存）。

### 第 2 步：事实核查（code-explorer，按需）

- 计划引用的既有文件、既有行为、行号区间做抽查：派 1-2 个 code-explorer 实例（只读勘察）核对计划断言与代码现状。事实核查实例不计入 `reviewInstances`——它只核对事实，不承担默认两视角的评审判断。
- 核查对象四类：文件路径与行号区间是否真实；对既有行为的断言（"某函数现在返回什么"）是否成立；对依赖存在性的假设是否有效；对接口、函数签名的跨步骤引用是否一致。
- 断言失实（文件不存在、行为描述错误、行号对不上）→ 记入视角一问题清单并标阻塞；本步只核查事实，不改计划。
- **设计输入证据（内部规则-17）抽查**：`completed` 行证据路径存在且内容与角色/实例声称相符（`#sha256` 复算一致、誊录来源可回指）；`self` 行依据与理由（含「无等待通道」判据）与 `waived` 行用户裁决引文可回指。本项**不因本步跳过而免**（主会话直读文件即可，不必派实例），证据失实记视角一阻塞项。
- 小计划或纯新建项目（无既有代码可查）可跳过本步；设计输入证据抽查不因本步跳过而免（内部规则-17）。

### 第 3 步：视角一——工程（默认，必执行）

工程经理姿态：先把范围与架构钉死，再看测试。四个检查块依次过。

**范围挑战（Scope Challenge）**

- **改动面嗅探**：统计计划的新建/修改文件清单与触及的模块数。超过 8 个文件、或引入 2 个以上新模块/新服务，即视为范围异味（本条只判范围；评审实例分档阈值另见「评审实例模式」节，含步骤数）：要求计划给出拆分论证——为什么同样的目标不能用更少的活动部件达成；论证不成立即阻塞，建议拆成多份独立可交付的计划。合格的论证说出"少一个部件会损失什么"；"将来会用到"不是论证。计划缺文件清单时，先要求补清单再嗅探，不凭步骤描述倒推估算；清单以目录级包布局表或"按目录组织"式汇总陈述、未逐文件展开的，同样视为缺清单（汇总表算不出文件数与模块数）——先要求按文件级（新建/修改逐文件列出）补全再评，清单形态与嗅探结论一并记入评审记录。
- **既有资产复用**：计划的每个子问题，问仓库里是否已有部分或完整解；已存在的流程能否直接复用其产出，而不是并行新建一条。重建已存在能力而未说明理由（重构收益、原实现不可扩展），记阻塞；理由成立则改为引用既有资产。
- **最小变更集**：砍掉哪些工作仍不阻塞核心目标？逐项过一遍"推迟它，验收还成立吗"；被砍掉的工作必须有显式去处（写入计划的范围外清单或未决项），不许蒸发。
- **新依赖质询**：计划引入新模式、新组件、新库时，确认运行时或框架没有内建等价物（标准库、平台原生能力、已安装依赖依次排查）；为几行代码引入一个新依赖即记问题。
- **交付物分发**：计划产出新的可安装工件（命令行程序、库包、镜像）时，构建与分发方式在计划内还是被推迟？没有分发渠道的代码没人用得上；推迟可以，但必须显式写下来并给理由。

**架构锁定检查**

- **数据流**：计划写清数据从哪来、经过什么转换与校验、落到哪、以什么形态离开；关键链路值得一张 ASCII 图而计划没有，记问题。
- **错误传播**：上游失败如何传到下游、在哪一层兜底、兜底后用户看到什么；每条会失败的路径在计划里有没有名字。只写"处理异常"而不点名错误类别的步骤，等于没有错误处理。
- **依赖方向**：新组件依赖谁、被谁依赖；是否引入循环依赖或反向依赖；新产生的耦合是否有正当理由。改完之后依赖图更清晰还是更纠缠，是架构锁定成败的直观检验。
- **生产故障预演**：每个新集成点描述一个现实的故障场景（超时、级联失败、数据损坏），计划是否交代了应对；预演不出的集成点说明计划对其假设过多。
- **回滚姿态**：交付后立即出问题怎么退——版本回退、功能开关、迁移回滚，各自多快；没有回滚答案的计划记问题。

**测试策略核对**

- 每步的"验收："行真实可执行：写明命令加期望输出或退出码、或明确的检查点；"运行测试确认通过"这类无法判定的验收即是计划缺陷。
- 分支覆盖意图：计划中的每个条件分支与错误路径是否指名了对应测试；未覆盖的分支逐条列出。错误路径没有测试，Prime Directives 的"零静默失败"就无从验证——这一条与视角二联动。
- 回归意识：改动触碰既有行为时，计划是否带了回归验证；改了行为而没有回归验证，标阻塞。
- 测试层级合理：多数单元、少量集成、极少端到端；倒金字塔的计划记问题。横跨三个以上组件的常见用户流，建议集成或端到端测试而非纯单元覆盖。

**认知模式检查清单**（工程经理的判断直觉，逐条对照计划）

1. **两周做不完的计划必须拆**：称职工程师两周内做不完一个"小"特性，说明问题出在结构而不是工作量，先拆再评。
2. **创新代币有限**：同一时间只允许引入一个不熟悉的技术，其余全部用被验证过的成熟方案；计划里出现第二个新变量就质询。
3. **渐进绞杀优于推倒重写**：能分阶段替换的就不要一次性切换；计划要求"一口气切过去"时，检查是否真的不存在渐进路径。
4. **先让改动变容易，再做容易的改动**：结构性调整与行为变更不得塞进同一步；混排即要求拆成先后两段。
5. **爆炸半径思维**：每个关键决策问一句"最坏情况波及多少系统、多少人"；答不上来说明锁定不足。
6. **为凌晨三点的人设计**：计划隐含的流程要按疲惫状态可执行来检验，不依赖某位英雄的临场发挥。
7. **可逆性优先**：用开关、灰度、增量迁移把犯错的代价降下来；不可逆的一步到位方案需要专门论证。
8. **区分本质复杂性与自造复杂性**：新增的每样东西都要回答——它解决的是真实问题，还是前面某步自造出来的问题？

用法提示：这八条不是逐条打钩的表格，而是对照计划时的提问姿态——评架构时用第 2、5、8 条，评拆分与排期时用第 1、3、4 条，评上线与回滚时用第 6、7 条。命中任意一条，就把对应的计划段落翻出来核对，找不到答案即记问题。

### 第 4 步：视角二——CEO/创始人（默认，必执行）

创始人姿态：容不下静默失败，盯范围与账本。先吸收视角一结论，再过两个检查块。

**Prime Directives 检查清单**

1. **零静默失败**：每条会失败的路径都有名字（具体的错误类别）、有处置（重试、降级或上抛并附加上下文）、有用户可见的结果；三者缺一即阻塞。过关锚点：把计划里每个新步骤问一遍"它失败时谁会知道"；答案若是"没人"，就是静默失败。
2. **数据流四条影子路径**：每条新数据流除主路径外，空（输入缺失或空集合）、慢（超时或迟到）、错（上游报错或格式坏）、坏（数据部分损坏或过期）四条影子路径都要有答案。过关锚点：能对每条流说出四条影子路径各自落到哪个分支。
3. **可观测性是范围的一部分**：新链路的日志、指标、告警写进交付物清单；"上线后再补可观测性"记问题。过关锚点：交付后三周有用户报障，仅凭日志能否还原当时发生了什么。
4. **延期必须显式写下来**：计划推迟的每一项都落纸面，带一句话理由与回头条件，并给出新的时间或触发条件；口头"以后再说"不算推迟，算丢失。过关锚点：范围外清单里每一项都能指到它将来被重新拾起的条件。
5. **交互都有边界情况**：双击、中途离开、慢网络、旧状态（页面放了半小时会话已过期）、并发操作，每个面向用户的交互逐个有交代。过关锚点：任挑一个交互，问"用户连点两次会怎样"，计划有答案。
6. **为六个月后的自己优化**：计划若只解今天的问题却给下季度埋雷（新债、路径依赖、知识集中到单人），显式点破，不当场放行。过关锚点：一年后新人读这份计划，能看懂为什么这么做吗；被绕开的旧路径会不会变成无人敢动的禁区。
7. **允许说"推翻重来"**：评审发现根本性更好的路线时，直接摆出来交用户裁决，不为已经花掉的规划成本辩护。过关锚点：诚实回答一句——如果今天从零开始，还会选这条路线吗；答案是否定的，就该把替代路线摆上桌面。

**范围模式门**

先判定当前计划处于哪种范围模式（判定依据用户处境与计划形态，模式由用户确认、评审只提议），再检查计划内容与模式是否匹配：

| 模式 | 适用处境 | 评审姿态 |
|---|---|---|
| 扩张 | 绿地新特性，用户明确想做大 | 问"更有野心的版本长什么样"，扩张项逐条摆给用户挑选，不静默塞入 |
| 收敛 | 在既有系统上迭代增强 | 当前范围是基线、按最大严格度审；值得做的扩张机会单独列出供挑选 |
| 持有 | 缺陷修复、重构、加固 | 范围既不扩也不缩，全力过全部检查单 |
| 收缩 | 计划明显过度或方向存疑 | 找达成核心目标的最小版本，其余全部出局或转未决项 |

- 不匹配信号：收缩模式里夹带扩张性功能、持有模式里"顺手升级依赖"、扩张模式的野心没有配套验收。命中即记问题。
- 模式一经确认，评审按该模式执行到底；中途要换模式，回用户重新确认，不静默漂移。
- 视角一的结论带入本门：视角一判"范围过大"时，默认按收缩或持有姿态把计划重过一遍。
- 情境默认值（只是建议，用户可推翻）：绿地新特性默认建议扩张；既有系统迭代默认建议收敛；缺陷修复与重构默认建议持有；计划触及文件明显过多时建议收缩。
- 姿态随模式变、检查单不变：任何模式下 Prime Directives 七条照过；收缩模式只是把"更完整版本"的建议降为记录在案，不是跳过质量检查。

### 第 5 步：可选加深（视角三/四）

两默认视角完成后，按计划形态判定是否建议加深，用户点头才执行（用户主动点名某视角时直接执行）：

- 计划含对外暴露的接口面（API、CLI、SDK、库函数、命令输出）→ 建议执行**视角三：开发者体验**。
- 计划含面向用户的界面、文案或交互流 → 建议执行**视角四：设计**。
- 两者都不涉及 → 说明跳过理由，直接进入第 6 步。
- 可选视角的启用判定与跳过理由写入评审记录；其发现按同一四元组格式记录，不与默认视角的发现重复计数。

**视角三：开发者体验（可选加深）**

站在接口的另一侧想问题：计划定义的每个入口，都是别人开发路上的一个台阶。检查项：

1. **时间到 hello-world**：从零安装到第一个可见的成功输出，计划能否说清是几步、多长时间；说不清即记问题。
2. **错误信息可行动**：出错时使用者知道发生了什么、为什么、下一步改什么；只抛错误码或裸堆栈的路径逐条点名。
3. **默认值即正确值**：最简单的调用就有有用结果，不需要先读完文档再配参数；必填参数越少越好，每个参数都有合理默认。
4. **命名可猜测且一致**：不看文档能猜到的名字；同一套语法贯穿全部接口，动词与参数风格统一。
5. **渐进披露**：入门用法即生产可用，高级选项按需展开，不把复杂度前置到第一步。
6. **升级不恐惧**：破坏性变更有预告与迁移指引，版本语义明确；"以后再写迁移说明"记问题。
7. **无人值守可用**：能被脚本与流水线稳定调用——退出码语义明确、输出机器可读、无交互式提问卡住自动化；只考虑了人肉终端使用的接口面记问题。

**视角四：设计（可选加深）**

站在最终用户一侧想问题：计划里每个用户看得见的字与状态，都是产品的一次表态。检查项：

1. **文案一致性**：同一概念全计划只用一个名字，动词与产品语气统一，不混用近义词。
2. **状态可见性**：每个面向用户的特性，加载、空、错误、成功、部分五态逐一有交代；缺态即问题。
3. **空态是功能**：空状态写明用户看到什么、下一步能做什么；留白或一句"暂无数据"了事即记问题。
4. **信息层级**：用户先看到什么、再看到什么有明确排序；一屏一个主任务，层级靠排序而非堆砌。
5. **反馈闭环**：操作后多久知道结果、等待期间看到什么、失败后从哪里重试，三问都有答案。
6. **可达性基线**：键盘导航、对比度、触控目标尺寸在计划里被点名设计，而不是被默认成立。
7. **首用与惯用兼顾**：新用户第一次进入的引导路径与老用户的日常快捷路径都被考虑到；不为效率牺牲入门，也不为入门拖慢常用。

### 第 6 步：结论与落盘

- 按输出格式汇总各视角问题清单，写入 `docs/plans/<plan>-review.md`。
- **分节交互，一次一节**：逐节把问题呈现给用户——先视角一，过完再视角二，可选视角在其后。每节收尾给一行小结（本节几条、几条阻塞），小结确认后再进下一节；不把四个视角的问题一次倾倒给用户。每条阻塞项需用户知晓并表态——接受修订建议、或说明不改的理由——表态结果记入评审记录；用户不接受且理由不成立的，维持阻塞，不因沉默或疲态降级。
- 给出两态结论：通过，或不通过（按评审总则的判定条件）。
- 非阻塞项二选一处置：随修订一并处理，或转 OPEN-n 未决项；既不处理也不登记的"挂着"不允许。
- 结论为通过时提醒用户：进入 plan-execution 前，项目存在 `.sdd/` 体系时先过 spec-gate 的适用性判定矩阵（内部接口-2）。
- 结论为不通过时，评审记录写明退回原因集中在哪些块（范围/架构/测试/静默失败/模式失配），让 plan-writing 的修订有的放矢，不逐条复述。

**收尾自查**（给出结论前逐项确认，任何一项不成立就回到对应步骤补做）：

- 两默认视角都已执行且分节呈现完毕，可选视角的执行或跳过均有记录。
- 每条问题四元组俱全，位置可回指计划原文，阻塞判定有理由。
- 结论与判定条件一致：通过 ⇔ 已执行视角阻塞项清零。
- 评审记录已落盘 `docs/plans/<plan>-review.md`，重审时已标注取代记录。
- 结论行顶格独占、无列表前缀（机器契约 内部规则-8——照抄模板的列表形「- 结论：通过」必拒，门禁拒因会指认该形态）。
- 全部未决意见已登记 OPEN-n，评审记录与计划正文均无自由文本待办标记。
- 通过结论附带了 内部接口-2 判定矩阵提醒（`.sdd/` 项目）。
- 病根判定（内部规则-14）：评审发现的问题若病根是设计缺口（设计未裁决、与规格矛盾或已过时），处置方向＝回设计面（brainstorming 或 spec-writing 回流）修复后回计划修订，不以计划文本内打补丁为处置。收尾自查病根判定引用该修复设计决策节，未产出即修订未完成（重审阻塞）。评审记录每轮逐条标注 fix-induced（附「新发现位置∩上轮修复 delta」证据），缺失该标注的评审视为未完成。
- 实例模式（内部规则-16）：改动面嗅探已记录；超阈值实现类计划为 `independent`（≥2）或已拆小/用户显式豁免；低阈值 `self`/`mixed`/`ratified` 的 `reviewReason` 非空；独立/mixed 已按 v3 写 `reviewRound`/`reviewProvenance`（链身份、round=1 全 fresh、countable=fresh|reused 数）且与评审记录/实例台账一致；sidecar 三评审字段与评审记录一致。
- 评审发现举一反三：本次评审发现的每个问题，按元技能全局规则「自查举一反三」执行同类扫描（义务全文唯一载体在元技能，本条只做指针），逐条处置或记录排除理由后收口。

## 输出格式

每个视角的评审输出是问题清单，每条问题＝四元组＋fix-induced 标注（五字段）：

- **位置**：计划内的章节/步骤/行号；整体性问题写"计划整体"。
- **问题**：一句话陈述缺陷，引用计划原文关键词，可核查。
- **建议**：给 plan-writing 的修订方向（方向性提示，非实施依据），不代写修订内容。
- **是否阻塞**：是/否，附一句判定理由。判定标准：不修就可能导致执行失败、返工或结果不可验证 → 阻塞；改进型、锦上添花 → 非阻塞。
- **fix-induced**：本条是否由上一轮修复引入（是/否＋「新发现位置∩上轮修复 delta」证据）；逐条标注，缺失该标注的评审视为未完成。

清单纪律：每视角以最重要的问题为先，最多列 8 条；更次要的问题合并为一条综合性意见或转未决项——长清单等于没有清单，每条都要经得起用户追问。

问题条目示例（合格形态，四元组＋fix-induced 俱全、可核查、可执行）：

> 位置：步骤 4「运行失败测试」｜问题：验收行只写"测试失败"，未写运行哪条命令、期望哪段失败输出，零上下文执行者无法判定成败｜建议：改为具体命令加期望的错误信息片段｜阻塞：是——验收不可判定的步骤会让执行在第一步就卡死｜fix-induced：否（首轮发现）

通过条件：两默认视角全部执行且阻塞项清零；已执行的可选视角同样阻塞项清零。未执行的可选视角不产生义务，但其跳过理由写入记录。

结论措辞要求：结论行必须写出"通过"或"不通过"字样并附判定依据（各视角阻塞项计数），不写"基本可以通过""倾向通过""有条件通过"——两态之外没有合法表述；附带条件的事项一律转非阻塞问题或 OPEN-n。

## 常见反合理化

评审途中冒出以下念头时立即停下——每一条都是绕过出口门或降低评审强度的合理化话术：

| 念头 | 反驳 |
|---|---|
| "计划大体没问题，剩下是小毛病不挡路" | 阻塞的判定标准是"不修会不会导致执行失败、返工或不可验证"，与毛病看起来大小无关；一条验收不可判定的"小毛病"足以让执行在第一步卡死。 |
| "用户等着开工，先给通过、意见以后补" | 出口门存在的意义正是拦住这句话：未经评审的计划进入执行被路由表互斥禁止；现在修订以分钟计，执行后返工以天计。 |
| "这是策略性计划，工程检查不适用" | 策略在实现细节处露馅。两默认视角无条件执行；某检查块确实零发现，写"无发现"，不整块跳过。 |
| "上一轮已经评过了，这次只改了一点" | 通过即快照：实质修订即作废重审。从既有记录出发可以让重评更快，免掉重审没有通道。 |
| "意见先口头说一下，记录回头再补" | 评审记录是评审的唯一载体，不落盘的评审等于没评；顺手也就顺手丢失了追溯链。 |
| "计划很大但都是文档/机械改动，自评就行" | 阈值只约束实现类计划，不按「看起来难不难」判；实现类且超阈值就必须 independent，或拆小/用户显式豁免，不能自评。 |
| "派了两个实例就是 independent" | independent 要求工程/CEO 两个默认视角各由一个首轮 fresh-context 实例承担；同一实例串两视角、或事实核查实例冒充评审实例都不算。 |
| "自评写得详细就等于独立评审" | 独立性看实例来源，不看文字长度；自评再详细仍是 `self`，超阈值计划不得以 `self` 通过。 |

## 与其他 skill 的接口

- learnings：正常收尾时提示记一条 learning（一句话 + 证据链接；允许显式说"无收获"跳过——跳过要出口，不沉默略过）。

- 上游：plan-writing——强制出口门（内部规则-4）。计划落盘后移交本 skill 评审；未经评审的计划不得进入 plan-execution（路由表互斥）。计划未成文、或修订后需重审，均回到 plan-writing。
- 下游：plan-execution——仅当结论为通过；`.sdd/` 项目在进入执行前先过 spec-gate 适用性判定矩阵（内部接口-2），本 skill 在通过结论里显式提醒。
- 重审回路：结论为不通过或计划实质修订时，闭环是 plan-writing 修订 → 回本 skill 重审；修订期间不经路由表改道去执行，也不由本 skill 代行修订。
- 事实核查：code-explorer（只读勘察 agent），1-2 实例抽查计划断言与代码现状的一致性；事实核查实例不计入 `reviewInstances`。
- 评审实例与凭据：默认两视角的 countable（fresh|reused）实例数入 sidecar `reviewInstances`（首轮全 fresh），模式入 `reviewMode`，理由入 `reviewReason`（内部规则-16）；独立/mixed 另须 v3 的 `reviewRound`/`reviewProvenance`（内部任务-191：链身份=plan:<planPath>、round=1 全 fresh、countable 只数 fresh|reused），派发按「评审实例派发提示词契约（v3）」执行；超阈值计划的实例义务与追认档适用边界以「评审实例模式」节为准。
- 跨插件（spec-gate）：评审中发现的规格层缺陷或歧义，经路由表回 spec-writing 处置，不在此处代改；对规格文档本身的评审意见处置归 spec-gate 的 review_disposition（内部规则-7 预告，双处置禁止）；跨会话未决意见登记 OPEN-n（内部接口-8）。
- 本 skill 只写 `docs/plans/` 下的评审记录，不写 `.sdd/` 下任何文档。

## 边界与禁止项

- 评审对象是计划文档，不是代码：已写代码的质量归 code-review；本 skill 不读 diff 评实现，也不给实现级意见（那是 plan-writing 修订时的事）。
- 不处置规格文档本身的评审意见：归 spec-gate 的 review_disposition（内部规则-7 预告）；本 skill 发现规格问题只登记与回流，不双重处置。
- 不执行计划、不改计划正文：执行归 plan-execution，修订归 plan-writing；本 skill 唯一落盘产物是评审记录。
- 只写评审记录，不代改规则（含权限规则与治理规则）：放行判据来自规则本身——评审中发现 AGENTS/闸/规格等规则缺陷，按规格问题回流登记（改规则须走计划链 plan-writing→plan-review→plan-execution），不得在评审内顺手改规则再让计划通过。
- 禁止并行执行四视角（B-M3-1）：默认顺序 视角一→视角二 串行；视角三/四在其后按需执行，同样不与其余视角并行。
