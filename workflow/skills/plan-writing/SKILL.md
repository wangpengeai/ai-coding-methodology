# plan-writing：实现计划写作

把已批准的设计翻译成一份执行者零上下文也能照做的计划。计划的读者画像决定写法：一位称职的开发者，但不了解本仓库、不了解这个领域、也未必擅长测试设计——计划必须把这个人需要的全部信息写进去，而不是写给还带着本会话记忆的自己。本 skill 的唯一产物是一份计划文档；出口是 plan-review，不是执行。

写者权限不等于执行批准（内部接口-6）：本 skill 的授权止于把设计翻译成计划——写了计划不构成实现许可，放行判据在 plan-review 评审通过与路由表命中「计划已批准」行，不在写者自身。

## 适用场景

- 设计决策已过 brainstorming 批准门（或用户带着已定方案直接说"出计划"），要把它变成可执行的步骤清单。
- 与 brainstorming 的分界：方案的产生与批准在先，本 skill 不承载设计决策的辩论；与 plan-review 的分界：本 skill 写计划，评审与放行归 plan-review。
- 进入条件由 workflow 路由表唯一判定，本 skill 不自定义。

## 流程

### 第 1 步：核对入口

- 确认设计决策已获明确批准——入口批准凭据按下条形态核对。
- **可接受的批准凭据形态（内部规则-12）**：①brainstorming 批准门通过记录；②用户带着已定方案直接指示"出计划/写方案"；③经核实的评审意见清单（已过 code-review 接收章验证四问、含逐条处置状态）+ 用户修复指令。凭据来源在计划 frontmatter 以 `decisionSource` 字段留痕（形态建议：`<来源>|<任务号或评审记录路径>`）。三者以外一律退回 brainstorming，本 skill 不代行批准。
- **设计面核验（内部规则-14）**：凭据核对后、进入勘察前，通读任务相关设计面——已批准设计决策/ADR、specs 相关模块分册与接口条目、docs/design-docs 相关设计回写，核查三类明显缺陷：缺口（该裁决的行为/边界/错误面未裁决）、矛盾（设计与规格或设计与设计冲突）、过时（引用面已被后续批次推翻）。发现缺陷的处置优先级：默认退回修设计——设计决策缺口回 brainstorming、规格缺口/歧义走 spec-writing 回流，修复后回本 skill 续写；仅当缺陷不影响本计划正确性**且用户显式同意延后**才转 OPEN-n 续行——OPEN-n 是兜底不是默认出口。核验结论写入计划头部「设计面核验」小节（无缺陷／缺陷清单与逐条处置）。plan-review 不通过后的修订前置同 内部规则-9（内部决策-069 D1）。
- **未决项排查（内部规则-15，内部决策-049）**：设计面核验同位，按任务域检索 `内部规格`（或项目声明的权威台账）相关未决项并显式处置——义务全文唯一载体在 内部接口-8 §7.1（消费面义务），本 skill 只做指针、不转述判据（防双写漂移）；与设计面核验同为开工核验动作、相邻不混同。处置留痕进计划头部新增「未决项排查」小节（仿「设计面核验」小节形态：无命中／命中清单与逐条处置）。
- **批次级基线收缩联动（内部规则-20，内部决策-060 修正案 1）**：核对本批变更是否触及既有模块的未锚 A 行——触及模块的未锚 A 行应在**同批收缩**（结构化锚或显式 waiver），或在计划「未决项排查」/证据中显式登记「本批不收缩」理由与回头条件；`内部规格` 的 baseline 只收缩（已锚残留基线即违例，不得靠「不动就不缩」积累库存）。
- **设计输入凭据（内部规则-17）**：第 2/3 步的依赖型委派（code-explorer 勘察、code-architect 设计）必须先返回并留痕，才进入第 4 步；计划头部按格式契约第 7 条写「设计输入」节。实例台账须登记（`内部台账<任务号>.md`；角色/实例标识/宿主类型/可续性；过程文档）；依赖型委派选择通道时优先可等待/可续入口（适配层桥接清单的列出/等待/续聊；无桥接清单时用持久成员通道），一次性派发仅作非阻塞输入；复用与再水化按元技能全局规则「代理实例复用与再水化」执行。依赖型委派须走**可等待通道**（委派方能在继续前取得报告正文并确认完成：宿主同步/可 join 的委派工具，或可 wait/可续聊的适配层桥接清单入口（无桥接清单时用持久成员通道）；**不写死宿主工具名**）；**fire-and-forget** 委派不得作为唯一设计输入来源。当前会话不持有可等待通道时按无子代理能力处置：主会话 self 留痕（附依据与理由，含「无等待通道」判据），或把委派交回持通道的会话/用户裁决；**不得把未返回的报告记为 completed**。机器可证＝节/角色行形态、证据可定位、声明哈希未漂移；不可证＝实例真实性、报告内容、落笔时序、waived 的用户授权真实性（由 plan-review 事实核查与用户确认承载）。
- 范围检查：任务横跨多个可独立交付的子系统时，建议拆成多份计划，每份独立可运行、可验证；经用户同意后逐份处理。

### 第 2 步：勘察（code-explorer，可并行）

- 按侧面分派 1-3 个 code-explorer 实例并行勘察，例如：目标特性的现有执行路径、相邻特性的既有模式与约定、数据存储与流转。
- 收集每份报告的 file:line 证据与必读文件清单。
- 禁止跳过勘察凭想象写计划：计划中引用的每个既有文件与既有行为，都应有勘察依据。

### 第 3 步：设计（code-architect，可并行）

- 调用 code-architect 产出实现蓝图：2-3 个实质不同的实现路线（组件设计、新建/修改文件清单、数据流、分阶段构建序列）加推荐与理由；可开 2-3 个实例各领一个侧面或倾向，汇总对比。
- 文件清单涉及全局接口且项目 `.sdd/` interface_registry 显示未注册时，先把"需先注册再实现"报给用户；注册落盘走 spec-gate（内部接口-7）。
- 方案对比限定在已批准设计下的实现路线；对比中冒出的新决策点（超出已批准范围），停下带回用户裁决或退 brainstorming，不静默拍板。
- 推荐路线经用户认可后写入计划。

### 第 4 步：拆解任务

- **先定文件结构**：按文件清单映射新建/修改文件与各自职责；沿用仓库既有组织方式；一起变更的文件聚在一起，按职责切分而非按技术层切分。实现类计划的文件清单必须文件级——新建/修改逐文件列出（含路径与一句话职责）；目录级汇总表或"按目录组织"式描述不构成文件清单（plan-review 的改动面嗅探按文件级清单计算，汇总表无从计算）。
- **任务尺寸**：一个任务是自带一轮完整验证周期的最小单元——小到可以单独评审通过或否决，大到值得单独验证。每步只做一个动作，量级以分钟计：写失败测试 → 运行确认失败 → 最小实现 → 运行到绿 → 提交。
- **零上下文假设**：执行者只读自己那一步。每步自带精确文件路径（修改处带行号区间）、完整代码或命令、预期输出；跨任务使用的函数签名在产出它的步骤里写全，后续步骤原样重复，不写"同上"。
- **每步必须带验收行**（格式见「计划格式契约」）：写明验证方式与预期结果——命令加期望输出或退出码，或明确的检查点。
- **三纪律**：DRY——出现真实重复才抽象，不为假想的未来需求建抽象；YAGNI——每步只实现该步验收所需的东西；TDD——先写失败测试再写实现，测试代码完整写进计划。
- **来源意见的处置状态（内部规则-9）**：计划步骤若来源于评审/勘察意见，须逐条携带处置状态——已验证采纳（附验证依据）/ 已验证驳回（附驳回理由）/ 转 OPEN-n（登记编号）。来源为非插件评审的意见（外部勘察、宿主 plan 模式勘察、会话内顺手发现），入计划前先过 code-review 接收章同款验证：意见是否属实（有证据吗）、是否指向真问题、是否指向规格歧义（是则走 spec-writing 回流而非直接照改）、处置是否可验证；未过验证的意见不得变成计划步骤。计划修订前先产修复设计决策节；来源意见的建议文本不得直接作为修订依据（内部决策-069 D1）。

### 第 5 步：落笔前自查

- 规格覆盖：已批准设计与规格条目逐条对照，每条能指到对应任务；有缺口先补任务。
- 空洞步骤扫描：搜"细节待补""类似上文""酌情处理"式表述，全部替换为实际内容；只有意图没有做法的步骤是计划缺陷。
- 命名一致：跨步骤引用的函数、类型、参数名前后一致。
- 引用核实：specRefs 中每个编号可回指真实规格条目或已登记 ADR。
- 来源意见处置复查：凡来自评审/勘察意见的步骤，处置状态四态俱全（含转 OPEN-n 的编号）；非插件评审来源的意见已过验证与规格歧义判定。
- 收尾审查（内部规则-11）：实现类计划（含代码或 skill 资产修改步骤）的收尾节含 code-review 步骤（三维派发或用户点名的等价评审）**与「learnings 沉淀」步骤**；learnings 的排序约束与两出口见格式契约第 5 条（不在此重复）；纯文档计划显式豁免并记录理由——「照计划步骤走完」不构成完成，收尾审查是完成声称的前门。
- 自查发现举一反三：本次自查发现的每个问题，按元技能全局规则「自查举一反三」执行同类扫描，逐条处置或写明排除理由后收口——义务全文唯一载体在元技能，本条只做指针、不转述判据。
- 契约改造冻结（C4）：凡触及 `workflow/skills/**`、`内部规格**` 正文或哈希登记的契约改造类计划，须**先冻结契约文本**（D 表/字段表定稿并入计划）再实现；文本修订与 IF 哈希重登同批一次完成，禁止收尾期边改边重登。

### 第 6 步：落盘与出口

- 保存到 `docs/plans/<主题>.md`；同名主题可加日期前缀区分。
- 落盘后唯一出口是 plan-review（强制出口门）：把计划移交评审；评审通过前，路由表不放行 plan-execution。
- 项目存在 `.sdd/` 体系时，提醒用户：评审通过后、进入执行前，先过 spec-gate 的适用性判定矩阵（内部接口-2）。

## 计划格式契约

计划文档同时服务两类读者：零上下文执行者与 spec-gate 校验器。格式契约（内部接口-1）：

1. **frontmatter 必须含 `specRefs` 数组**，元素为规格条目编号（`FR-域-n` 形态）或已登记 ADR 编号（`ADR-NNN` 形态），两种形态至少其一非空。追溯口径（内部接口-1）：有效需求引用即可独立满足一般追溯——仅当计划涉及实际决策（采纳/沿用某条已批准设计决策）时才引用对应 ADR，不得为满足格式制造无实际决策的 ADR 引用；悬空引用（编号回指不到真实条目）仍判 blocking。最小示例：

```markdown
---
specRefs: [内部需求-1, 内部决策-002]
---
```

2. **每个步骤标题的下一行必须是以「验收：」起头的单行**，写明该步的验证方式与预期结果。示例：

```markdown
### 步骤 2：运行失败测试

验收：`node workflow/scripts/check-routing.mjs` 退出码为 1，violations 恰含 1 条。
```

3. **校验归属与强度**：以上两项由 spec-gate 的 plan 模式校验。缺 `specRefs` 为 warning「计划未追溯规格」；步骤缺验收行为 warning「步骤无验收」；引用的编号在规格体系或 ADR 登记中不存在为悬空引用，判 blocking。默认强度为提醒，显式开启校验开关后 blocking 生效；项目无 `.sdd/` 体系时 plan 校验整体跳过、不报错；诊断可回指计划行号。
4. 建议项（非校验对象）：计划头部写目标一句话、实现路线两三句、全局约束逐条列出——所有步骤默认继承全局约束，各步骤不再重复。
5. **实现类计划的收尾节必须含 code-review 步骤与「learnings 沉淀」步骤**（内部规则-11；纯文档计划显式豁免并记录理由）。learnings 沉淀须位于 verification / 完成链步骤之前（写入时点＝verification 签发前，见 learnings skill 的冻结前约束），且带两条出口：有收获→`经验记录`（一句话＋证据链接）；无收获→显式声明「无收获」＋理由。本条由 plan-review 受理清单承载（core 校验器哈希冻结，不做机器诊断）——计划缺收尾审查或缺 learnings 沉淀即允许执行以未评审 diff 宣称完成，或以事后提醒冒充计划内必过步骤。
6. 写计划时即按本契约自查，不等校验器兜底。
7. **实现类计划的计划头部必须有「设计输入」节**（内部规则-17；纯文档/无设计面计划可单行整体豁免，但仍须是该唯一 H2 节）。角色行固定形态：`- <角色>：<实例标识或「主会话自评」>｜<证据>｜<completed|self|waived>`；非角色行（如 `- 说明：…`）忽略。`completed` 的证据为**仓库根相对路径必填**（常规文件、非空、非目录、非计划自身、不越界），可选后缀 `#sha256:<16-64 hex>`（检查器按 LF 归一复算；主会话誊录报告须在证据文件头注写明来源实例与誊录事实）；`self` 须写自评依据与理由（含「无等待通道」判据）；`waived` 须写用户显式裁决引文与时间，整体豁免写 `- 设计输入：waived｜<理由或用户裁决引文>`。节须位于首个步骤/任务标题之前，frontmatter/代码围栏/HTML 注释内不计。机器检查由 workflow 侧 `workflow/scripts/check-plan-design-input.mjs` 承载（plan-review 受理核对执行；**exit 0 通过 / exit 1 违规 / exit 2 工具错误**）；**不进 spec-gate core 校验器**（内部规则-9 哈希冻结，不改变 内部接口-1 的 core 校验面）。旧计划重审按同契约补记；证据不可回溯时以 self/waived 如实留痕。
8. **实现类计划的计划头部必须有「多宿主适配评估」节**（内部决策-056 / 内部规则-18；纯文档/无宿主面计划可单行整体豁免，但仍须是该唯一 H2 节；标题为 `## 多宿主适配评估`，允许尾随括注）。义务：新增/变更任何插件功能面（skill/command/agent/hook/事件/配置/清单/适配能力）时，**逐宿主/逐功能面**评估并如实记录；状态词闭集＝`已适配并真机验证`／`已适配未真机验证`／`本批不适用`（附 ≥4 字理由）／`无验证条件`（附 ≥4 字理由）；行形态 `- <对象>：<状态词>｜<证据或理由>`，前两态第三字段为仓根相对路径（可带 `#sha256:<16-64 hex>`，LF 归一复算）；不得把「未验证」「无验证条件」写成「已适配」「已验证」；整体豁免行 `- 多宿主适配评估：整体豁免｜<理由>`（实现类计划禁用；与评估行并存即歧义）。节须位于首个步骤/任务标题之前（步骤标题口径与 spec-gate plan 校验一致：`步骤`/`任务`/编号标题，H1-H6），frontmatter/代码围栏/HTML 注释内不计；前两态证据须为仓根相对路径、常规文件、非空、非计划自身、不越界。机器检查由 workflow 侧 `workflow/scripts/check-plan-host-impact.mjs` 承载（plan-review 受理核对执行；**exit 0 通过 / exit 1 违规 / exit 2 工具错误——不得进入通过结论、修复后重跑**）；**不进 spec-gate core 校验器**（内部规则-9 哈希冻结，不改变 内部接口-1 的 core 校验面）。
9. **实现类计划的计划头部必须有「测试锚定」节**（内部决策-060 / 内部规则-19；纯文档/无规格面计划可单行整体豁免，但仍须是该唯一 H2 节；标题为 `## 测试锚定`，位于首个步骤/任务标题之前）。节内行只接受**三类合法行形态**：①可执行锚 `- <ID>：<单元测试|集成测试|系统测试|验收测试>｜<仓根相对测试路径>#<用例标题片段>` 或 `- <ID>：命令冒烟｜<仓根相对脚本路径>`（第五类可执行锚，脚本须含 `--selftest`）；②**派生**锚 `- <ID>：派生｜<A-ID 列表>`（FR/IF 类条目指向验收条目链，引用 ID 须存在且非空）；③非可执行类别 `- <ID>：<构建期检查|人工走查|审查清单>｜<≥8 字理由>`。`- 说明：…` 旁注行显式忽略；本批无新增/变更规格条目时单行 `- 测试锚定：n/a｜<≥8 字理由>`；纯文档/无规格面计划可 `- 测试锚定：整体豁免｜<理由>`（实现类计划禁用；与其他任何行并存即歧义）。节内 ID 须在规格中存在；可执行锚须语法合法（路径形态、`.test.mjs` 后缀、片段非空）；路径存在性与片段唯一性由仓检查器在实施收尾校验（计划门不因同批新建测试尚未落盘而误判）。**实现类整体豁免禁用判定必须 import `workflow/hooks/routing-lib.mjs` 的 `planChangeSurface(...).isImplementation`**（单点判定，不得自造第三判定源）。机器检查由 workflow 侧 `workflow/scripts/check-plan-test-anchors.mjs` 承载（plan-review 受理核对执行；**exit 0 通过 / exit 1 违规 / exit 2 工具错误——不得进入通过结论、修复后重跑**）；**引入批过渡**（检查器尚未落盘、由本批计划引入时）：受理核对以静态核对本条与计划节形态替代并记录，checker 落盘后同批补跑，不得静默跳过；**不进 spec-gate core 校验器**（内部规则-9 哈希冻结，不改变 内部接口-1 的 core 校验面）。

## 工具

两个 agent 均为只读（frontmatter 工具集不含任何写类工具）；落盘由本 skill 主会话完成，agent 不落盘。

| agent | 用途 | 调用范式 |
|---|---|---|
| `code-explorer` | 勘察：追踪既有特性执行路径（入口、调用链、数据流、分层），产出 file:line 引用与必读文件清单；只输出事实 | 第 2 步并行 2-3 实例，各领一个侧面 |
| `code-architect` | 设计：多方案对比（组件设计、新建/修改文件清单、数据流、分阶段构建序列）加推荐与理由；产出文件清单时执行 interface_registry 注册检查（内部接口-7） | 第 3 步单实例出多方案，或并行 2-3 实例各领一个侧面/倾向 |

## 与其他 skill 的接口

- learnings：收尾节契约见格式契约第 5 条（learnings 沉淀须在 verification 前）；正常收尾记一条 learning（一句话＋证据链接）。条目格式与冻结时点归 learnings skill。

- 上游：brainstorming——批准门通过的设计决策是本 skill 的输入；其 Architectural 档移交 spec-gate 定稿的 ADR 编号可进 specRefs（内部接口-6）。设计未过批准门：拒收并退回。
- 下游：plan-review——强制出口门。计划落盘后必须经其评审；未经评审的计划不得进入 plan-execution（路由表互斥）。评审记录由 plan-review 落在 `docs/plans/` 下的同名评审文档。
- 跨插件（spec-gate）：specRefs 悬空引用由其 plan 模式诊断（内部接口-1）；`.sdd/` 体系存在时评审通过后过判定矩阵（内部接口-2）；接口注册检查读 `.sdd/` interface_registry（内部接口-7）。本 skill 不写 `.sdd/` 下任何文档。
- 跨会话未决项：按 内部接口-8 登记 OPEN-n，不留自由文本待办标记。

## 边界与禁止项

- 未经 plan-review 通过的计划不得进入 plan-execution；本 skill 不自行放行，也不直接开工实现。
- 规则冲突不得自放行：写作中发现权限/治理规则（AGENTS、hooks 闸、规格）与任务目标冲突时，把冲突处置记入计划或呈报用户裁决——先改规则给自己放行再继续，正是闸侧固定上界要拦的绕行路径。
- 禁止重新辩论已批准的设计决策；实现路线对比中冒出的新决策点，带回用户或退 brainstorming。
- 写作中发现设计缺陷时默认处置＝退回修设计（内部规则-14）：决策缺口回 brainstorming、规格缺口/歧义走 spec-writing 回流；转 OPEN-n 或计划内打补丁续行仅限不影响本计划正确性且用户显式同意延后——带病进入执行即二次返工，返工面是已执行批次。
- 禁止跳过勘察与设计直接罗列任务；禁止空洞步骤与跨步骤"同上"引用——零上下文执行者只读自己那一步。
- 计划文档是本 skill 唯一落盘产物，上界＝`docs/plans/` 下的过程 Markdown 文件（闸侧对 plan-writing 租约的固定写面上界与此同源，内部规则-16）；代码库零写入，勘察与设计全部经只读 agent 完成。
