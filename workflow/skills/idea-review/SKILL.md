# idea-review：想法评估（场景 A 唯一入口）

回答一个问题：这事值不值得做。产出是一份显式结论加一份设计文档，不是代码。

## 适用场景

- 用户带着一个尚未成形的想法来：一个新产品方向、一个想做的东西、一个"要不要做 X"的疑问，手头还没有任何 spec。
- 与 brainstorming 的分工：本 skill 处理"还不知道值不值得做"的想法；任务对象已明确、只是方案未定的，归 brainstorming。注意：新方向（新插件/新产品/方法论级新能力）即使对象表述得很明确，未经本 skill「值得做」裁决仍归本 skill——"对象明确"不等于"已裁决值得做"（2026-09-12 实测误判的教训）。这条分界由 workflow 路由表唯一判定，本 skill 不自定义进入条件。
- 硬边界：全程不写代码、不搭脚手架、不调用任何实现类技能。唯一的落盘产物是设计文档。

## 流程

### 第 1 步：定模式

先问一个问题：做这件事，你想得到什么？按答案选姿态（问题集不变，压力不同）：

- **严格模式**：有真实用户、商业意图或组织内立项诉求。姿态是诊断：每题追问到具体、可证、令人不适的深度；回答者感到舒适，说明还没问到底。
- **探索模式**：学习、兴趣、开源贡献、限时活动。姿态是热情的合作者：帮用户找到这个想法最让人兴奋的版本，收尾给可直接动手的构建步骤，而不是市场验证任务。

会话中途用户流露商业意图（提到客户、收入、立项）时，自然升级到严格模式，并说明接下来问题会变难。

### 第 2 步：六问（一次只问一个）

每题三件套：主问、过关标准（听到什么才算问透）、警示信号（什么回答是坏信号）。

1. **需求真实性**：别人要这个东西的最硬证据是什么——不是"有兴趣"、不是"留了联系方式"，而是"明天它消失了，谁会真的难受"？
   - 过关标准：具体行为。有人付钱、有人扩大使用、有人把日常工作流绑在上面、有人在你停机二十分钟后打来电话。
   - 警示信号："大家觉得挺有意思""五百人留了邮箱""投资人说这个方向热"。这些都不是需求。
2. **现状替代**：目标用户今天是怎么凑合解决这个问题的？那个凑合方案让他们付出什么代价？
   - 过关标准：具体的工作流、每周耗掉的小时数、花的冤枉钱、临时拼起来的工具、为此专门雇的人。
   - 警示信号："现在没有任何方案，所以机会大。"真的没有任何人在想办法，多半说明痛得还不够。
3. **绝望具体性**：说出最需要这个东西的那个具体的人。什么职位？什么事让他熬夜？这事做不成他会怎样？
   - 过关标准：一个名字、一个角色、一个具体后果（职业上的、一天里的、或创造力上的），最好是从那个人嘴里直接听来的。
   - 警示信号：品类级回答。"中小企业""营销团队"是筛选条件，不是人——你没法给一个品类发邮件。
4. **最窄楔子**：这个想法最小的、本周就有人愿意真金白银买单的版本是什么——而不是平台建好之后？
   - 过关标准：一个功能、一条流程；几天能交付、且有人会为它付钱的那个切入口。
   - 警示信号："得把整个平台建完才有人能用。"这通常说明价值主张还没想清楚，而不是产品应该做得更大。
5. **独有洞察**：你亲眼看着用户用它（或用替代品）时，哪件事出乎你意料？
   - 过关标准：一个违反预期的具体瞬间。用户拿产品去做设计目的之外的事，往往才是真正的产品在露头。
   - 警示信号："发了问卷""做了演示""一切符合预期。"问卷会说谎，演示是表演；"符合预期"说明正在拿假设过滤现实。
6. **未来适配**：三年后世界大概率不一样，那时这个东西变得更不可缺，还是更无所谓？
   - 过关标准：一个具体断言——用户的世界会怎样变、这个变化为什么让你做的东西更值钱。
   - 警示信号："市场每年增长百分之二十。"增长率不是愿景，每个竞对都会念同一句。

提问纪律：

- 一次只问一题，等回答再问下一题。
- 对每个回答表态，并说明什么证据会改变你的判断；不说"这个想法很有意思"这类空话。
- 首个回答往往是打磨过的版本，至少追问一次再往下走。
- 用户此前已回答清楚的题，跳过。
- 用户明显不耐烦时：按其所处阶段挑最关键的两题问完即放行；用户第二次表示想跳，尊重并直接进入第 3 步。

### 第 3 步：前提挑战

给方案之前，先把想法底下垫着的前提翻出来晒一遍：

- 这是不是对的问题？换一种问法，会不会存在简单得多或影响大得多的解？
- 什么都不做会怎样？痛点是真实发生的，还是想象中的？
- 仓库里、市面上，已经有什么部分解决了它？哪些可以直接复用？
- 若交付物是新工件（命令行程序、库、镜像、应用）：用户怎么拿到它？没有分发渠道的代码等于没人能用，设计必须包含分发方式，或显式推迟并说明。

把前提写成编号清单，逐条让用户明确表态同意或不同意；有不同意就修正理解、回到相应问题重问，然后重新过一遍前提确认。

### 第 4 步：方案对比门（强制 2-3 个）

单一方案不得过门。即使某个方案看起来"明显会赢"，也必须摆出对照项让用户选择。

产出 2-3 个实质不同的做法，每个包含：一句话概要、体量（S/M/L/XL）、风险（低/中/高）、两条优势、两条劣势、可复用的既有资产。

- 其中一个必须是**最小可行版**：动的东西最少、最快能交到用户手里。
- 其中一个必须是**理想架构版**：长期轨迹最好、结构最干净。
- 第三个可为横向思路：换个角度框问题的意外做法。

给出推荐及一行理由（对应用户在第 1 步声明的目标），然后把全部方案摆给用户明确选择。用户拍板前不得进入第 5 步——"方案显然会赢"仍是一个需要用户裁决的方案决定。

### 第 5 步：结论三态（必须显式给出）

评估结论只有三种，必须在离开本 skill 前显式说出并写入设计文档：

- **值得做**：写明依据与所选方案，交接 brainstorming 进入方案细化。
- **不值得做**：写明理由，以及"什么证据出现时应当重评"。
- **需补信息**：逐条列出缺失的具体信息与获取方式；其中跨会话仍悬而未决的问题按 内部接口-8 登记为 OPEN-n，不写成自由文本待办标记。

结论未显式给出前，不得引导会话进入 brainstorming。

### 第 6 步：设计文档

存到项目内 `docs/design-docs/<主题>.md`；不写用户主目录下的任何私有状态。

- 文档是决策记录，不是对话转录：每个决策一条加理由；会话中被否掉的方案只留一行（名字加否决理由），不复活整段论证；没有内容的章节直接省略。
- 首次原创（初始架构/方法论级设计）可直接归档（内部决策-039）：直接创建归档文档时，同文档记录来源证据（六问引语/数字/出处）、评估与复核结论、未决项去向即可，不要求先造过程文件再走移交；也不得反向虚构过程史——把不存在的评审/移交过程写进文档，过程资产移交与未决去向一律如实记录。原创评估归档不替代正式规格。
- 要素：问题陈述、关键证据（六问里拿到的具体引语与数字）、前提清单及确认结果、方案对比、推荐与理由、结论（三态之一）、开放问题、下一步动作（一个具体的现实动作，不是"去把它做出来"）。
- 同主题已有旧文档时，新文档头部标注取代了哪份，形成修订链。

## 与其他 skill 的接口

- learnings：正常收尾时提示记一条 learning（一句话 + 证据链接；允许显式说"无收获"跳过——跳过要出口，不沉默略过）。

- 上游：workflow 路由表把"提出新想法、无 spec"的唯一入口指到本 skill。
- 下游：brainstorming——仅当结论为"值得做"。交接时带上结论与所选方案，由 brainstorming 接手需求澄清与方案设计。
- 未决问题：跨会话未决项按 内部接口-8 登记 OPEN-n。
- 本 skill 不做任何规格落盘；项目使用规格体系时，规格写作由 spec-gate 管辖，与本 skill 的设计文档互不替代。

## 边界与禁止项

- 禁止启动实现：不写代码、不搭脚手架、不进入文件级技术设计；方案对比止于取舍论证。
- 不自定义进入或退出条件，判定权在路由表；与 brainstorming 的分界是"是否已有明确任务"。
- 单一方案不得过对比门；探索模式同样不得跳过前提挑战与方案对比。
- 结论三态未显式给出，不得进入 brainstorming。
- 设计文档只落项目内 `docs/design-docs/`；文档中不留自由文本待办标记，未决事项一律走 OPEN-n。
