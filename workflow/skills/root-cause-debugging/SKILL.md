# root-cause-debugging：根因调查与受控修复（调试场景唯一入口）

一切"实际行为与预期不符"的调查与修复都从本 skill 进（互斥规则 1：此场景禁用 plan-execution）。心脏是 Iron Law——无根因不修复；「快速通道判定」章是全体系 hotfix 三分类的唯一标准来源。

## 适用场景

- 症状类：报 bug、抛异常、回归（"昨天还好好的"）、测试意外失败、性能劣化——调查并修复一切"实际行为与预期不符"的问题。
- 疑问类：为什么挂、为什么慢、为什么结果不对——纯调查无修复意图时同样进入，产出是结论。
- 进入条件由 workflow 路由表唯一判定（互斥规则 1），本 skill 不自定义。
- 模式区分（调试自发现 vs 接收问题反馈）见下方「模式区分」小节——处置路径不同，判定机械判据在彼处。
- 两种合法终点：根因 + 修复 + DEBUG REPORT；或走完五阶段后的"外部/环境性问题"结论（记录已调查项与缓解方式）。调查不充分时，"找不到根因"只是"还没找到"，不构成第三种终点。

### 模式区分（内部规则-9，2026-09-13 修订；2026-10-14 内部任务-75 重组为独立小节）

按问题来源分两种模式，处置不同——

- **调试自发现**：执行其他任务过程中自行发现 defect（测试意外失败、行为与预期不符），根因与修复同属当前任务上下文，按本 skill 闭环直接修复（仍受 Iron Law/TDD/3-strike 约束）。
- **接收问题反馈**：用户直接把缺陷报告交给我（常附带已诊断的修法建议）——先用五阶段验证根因，再逐坑评估改动量：文案/局部小修在调试闭环内随修；凡动协议语义、规格、ADR、skill 行为契约或受控仓规（仓库维护说明 等行为契约文档）的——受控文档也是修复对象，行为修复同样是修复——转 `plan-writing` → `plan-review` → `plan-execution`，不在本 skill 内直接实施。路由命中调试入口不构成变更尺度许可。分类按 内部规则-9 机械判据执行：触及 hooks 闸/租约/签发/键控/协议状态格式或规格已登记行为的输出面 → 一律计划链，**行数不构成判据**（"只有一行"是合理化话术，见元技能红旗表）；逐坑分类结论须先于修复呈现并记入 DEBUG REPORT——先动手后分类即时序违规（2026-09-16 增补）。
- **分类检索清单（IMP-1，2026-10-14 内部任务-75）**：判定「无规格登记/可闭环小修」前，必须先完成规格权威面检索并留痕——检索面至少覆盖需求/总体设计/详设三层权威面（或本仓 specs 等价物；契约归属跨文档时按引用链扩面，台账行内明文引用的权威面必须入清单），并扩到 `内部规格`（或项目声明的权威台账）——按任务域检索相关未决项并显式处置，义务全文在 内部接口-8 §7.1、本 skill 只做指针不转述判据（内部规则-12，内部决策-049），处置留痕同落 DEBUG REPORT；逐面记录检索命令与零命中证据于 DEBUG REPORT；无检索证据的分类结论视为无效（与「先动手后分类即时序违规」同款机械口径）。「生产门禁」「安全边界」「契约语义」是「一律计划链」的显式触发词——目标行为涉及时无须等检索即可先判计划链（检索留痕仍须补足）。
- **判例（IMP-2，2026-10-14 内部任务-75）**：正例（可闭环小修）＝对齐已在权威面登记的既有约定——纯实现漂移、文案对齐、登记面先行而实现漏同步的对齐类；反例（必须计划链）＝生产门禁/安全边界/契约语义类行为变更——修法已在台账登记、有先例可循、TDD 全绿，仍属规格已登记行为。
- **基线写面（IMP-3，2026-10-14 内部任务-75，闸侧强制）**：声明本 skill 而未附 `--change-scope` 时，闸侧 Edit/Write 仅放行过程文档（docs/plans 的 `.md`）；代码/测试/归档面修改须以 `--change-scope` 显式声明写面后**沿原任务号重声明**（扩面不是换号）——被拦时按 deny 文案指引重声明即可，语义是「改什么」须显式，不是禁止修改。

## 流程

### Iron Law：无根因不修复

任何修复方案必须先答出两问：**为什么这个修复会消除该症状**，**为什么它不会引入新症状**。两问有一问答不上，就是根因还没找到。根因未定位之前，一行修复代码都不得提交（T-M4-1）——"先试试看"的修复、注释掉报错处的修复、"八成是这个"的修复，全部在此列。

理由：症状修复的代价不是这一次没修好，而是每盖一层症状，下一个真 bug 就被埋深一层，直到没人能看清系统本来的样子。

### 五阶段调查

顺序执行，前一段没有结论不进下一段。

**一、复现**：把错误信息读完整——栈、错误码、行号都不跳读，错误信息常常直接指认肇事层。确定稳定复现路径与频率，偶发问题量化到"N 次出现 M 次"；不可复现时先补观测（日志、埋点、监控窗口），带着证据回来，不空手猜。回归类问题立即查近期变更（受影响文件的提交历史与 diff）——回归的根因必然藏在变化里。

**二、隔离**：把触发条件削到最小——逐步删减输入、配置、步骤，直到"再删一处就不复现"，剩下的就是触发核。多组件系统先在组件边界取证：记录每个边界进出的数据与配置传播情况，先钉死"断在哪个组件"，再进组件内部查。

**三、假设**：列出 2-3 个候选根因，每个写成一句可证伪的话："X 是根因，因为 Y"。按解释力与验证成本排序。对照「已知 bug 模式速查」补漏——候选清单里没有高概率模式时，先自问是凭什么排除的。

**四、验证**：每个假设先设计判定实验再动手，实验结果无论正负都必须能推进判定：证实则进入定位，证伪则明确排除并记录排除依据。一次只验证一个假设、一次只改一个变量。实验手段取最小侵入（临时日志、断言、探针脚本）；验证性改动不是修复，取证后即撤。

**五、定位**：证据链闭合——"症状 ← 中间状态 ← 根因"的每一跳都有实验结果或代码证据支撑，并且整条链能回答 Iron Law 的两问。链上有断口就是没定位，回去补那一跳。

**3-strike 停手规则**：同一症状的调查中，连续 3 次实验失败（3 个假设相继证伪，或同一假设反复尝试 3 次）后必须停下来报告——写明当前证据、已排除项、还需要的信息（或需要的人），禁止"再试一次"：第 4 次尝试本身就是违规。停手不是失败，是规则；停手后需要跨会话跟进的事项按 OPEN-n 登记（内部接口-8），不写自由文本待办标记。

### 已知 bug 模式速查

假设阶段对照本表；命中模式时直接用「第一判定实验」开局，省一轮盲扫：

| 模式 | 常见信号 | 第一判定实验 |
|---|---|---|
| 竞态 | 偶发、随时序与负载变化，重跑即好 | 串行化疑点路径（加锁或单线程重放），复现随之消失即证实 |
| 边界条件 | 只在极值、空集、首末项出错 | 直接构造边界输入（空、单元素、上界值）跑单测复现 |
| 缓存失效 | 数据陈旧，清缓存即愈 | 绕过缓存直读数据源，比对两值差异 |
| 配置漂移 | 本地好、CI/生产坏 | 导出两环境实际生效配置逐项比对 |
| 隐式依赖 | 换机器、换版本即坏 | 在最小环境里逐项声明依赖版本后重跑 |
| 错误吞没 | 上层无感知，底层早已报错 | 全链路放开错误日志、临时移除兜底捕获，让真实错误冒头 |
| 集成契约不符 | 单测全绿，联调即挂 | 在服务边界抓包，比对实际请求/响应与约定 |

### 快速通道判定（内部接口-3：hotfix 三分类的唯一标准来源）

正常路径是：根因定位 → 最小复现测试 → 修复 → DEBUG REPORT。快速通道是对"规格先行"的受控豁免，判定标准全体系只此一处（单标原则）：spec-gate 不得自定义标准，本 skill 也不得增开新类。

"规格先行"只是顺序要求，不是对上游规格写作的禁止：本 skill 约束的是「受控资产先改、后补规格」的顺序违规；合法的上游需求/设计规格写作（idea-review/brainstorming 产出、spec-writing 的正常前置）照常先行，不因调试场景而需要绕经本入口。已定位的修复也不因"顺手先写个规格"洗白——写者权限不等于实施批准，受控资产的修改仍须计划链。

三分类（须同时满足所属判据与"等不起正常规格周期"）：

| 分类 | 判定标准 |
|---|---|
| 生产事故 | 线上不可用、数据损坏或用户可见故障正在持续，止血优先于流程 |
| 紧急安全修复 | 漏洞正被利用或已公开披露，暴露窗口每小时都在放大损失 |
| 高未知性探索原型 | 为消除关键未知性而写的抛弃式验证代码，产出是知识不是功能；默认不得进入生产路径 |

命中后的强制时序（T-M4-2）——**编码之前**完成向 spec-gate 的最小记录登记（内部接口-3）：

- 登记内容七项缺一不可：触发原因 / 范围 / 行为与验收假设 / 风险 / 验证计划 / 定稿触发点 / 接口影响声明；缺项即拒绝登记，不得进入快速通道。
- 登记成功产生 temporary-mitigation 状态的 ledger 条目与 follow-up deadline；deadline 由 spec-gate 台账跟踪（SessionStart 提醒、/gate 超期校验），超期未定稿阻塞后续非紧急变更。本 skill 只做判定与触发登记，不维护台账。
- 台账写入失败：维持 temporary-mitigation 状态并补录，不得放弃记录继续开发。
- 探索原型要保留并入主干：先完成正式规格，再谈保留。

三条不许绕：

- 三分类之外禁止自定义新豁免类别（B-M4-4）——"这个改动手头正好没人管"不是第四类。
- 快速通道豁免的是规格流程，不豁免调查纪律：事故中的止血动作（回滚、降级、摘流量）不是修复代码；修复代码仍受 Iron Law 约束，止血后必须补完根因调查并记入 DEBUG REPORT。
- 修复同时暴露规格缺陷时，与下文「规格影响判定」叠加执行，不互斥。

### 活跃事故车道（active incident lane，内部规则-6）

判定为生产事故时，五阶段调查**之前**先落事故协调事实（记入 DEBUG REPORT 的事因节，避免协调信息随会话丢失）：

1. 严重级（P0 全不可用/数据损坏 → P3 局部退化）与影响范围起点时间。
2. 事故负责人（Incident Commander）与沟通节奏（向谁、多久更新一次）。
3. 关键时间线骨架（发现/确认/止血开始各时点，随事态追加）。
4. 证据保全：日志/指标快照在止血**前**留存引用（回滚会冲掉现场）。
5. 止血动作（回滚/降级/摘流量）执行后，经 内部接口-13 在受影响 CHG 上留痕：
   ```bash
   node <spec-gate 安装根>/assurance/production.mjs --project-root <项目根> advance \
     --change CHG-n --to temporary-mitigation --incident-ref "<内部接口-3 条目引用>" --evidence '[{"subjectType":"incident","subjectId":"<id>","sourceRef":"<时间线/日志引用>"}]'
   ```
   （缺 incidentRef 即拒绝——旁路必须可追溯；项目无 CHG 记录时止血照常执行，留痕降级为 DEBUG REPORT 记录。）

止血完成 ≠ 事故闭环：进入既有五阶段根因调查；修复上线后 CHG 收敛（rolled-back 后重新发布走新 CHG）。

### 修复纪律

- **先写最小复现测试再修**（衔接 tdd）：测试在修复前失败（RED）、修复后转绿（GREEN，同一选择集），证据按 内部接口-5 格式记录。测试怎么写归 tdd，本 skill 只定"修复前必须存在"这条义务。
- 复现测试现实不可行时（依赖真实外部故障、特定硬件、无法自动化的交互），必须记录**原因与替代验证**——人工验证步骤与结果、日志取证、灰度观察期——写入 DEBUG REPORT 的"修复与验证"节。不可行是换一种可审计的验法，不是免验。
- 一次一个修复，最小 diff；"顺手"重构按 code-discipline 负向清单禁止。
- 同类错误已在别处实际发生过时，评估在相邻层加一道守卫防复发（防御纵深）；仅为假想场景加守卫属投机处理，同样被 code-discipline 禁止。
- 举一反三桥接注记（内部决策-043）：DEBUG REPORT「影响面：同模式代码点」与上条同类错误守卫即元技能全局规则「自查举一反三」在调试面的具体化——义务全文唯一载体在元技能全局规则，本节不另设第二判据、不转述；调试场景的同类扫描落点仍在影响面节。

### DEBUG REPORT

修复完成声称的必要条件是产出完整报告，按此格式：

```
DEBUG REPORT
症状：[观测到的现象，含发生频率与环境]
复现步骤：[最小复现路径；不可复现时写取证方式与证据]
根因：[定位结论 + 证据链：症状 ← 中间状态 ← 根因，逐跳列出实验/代码证据]
分类检索：[接收问题反馈模式必填：判定「无规格登记/闭环小修」前的逐面检索命令与命中/零命中证据；触发词命中直判计划链时检索留痕仍须补足（IMP-1）]
修复与验证：[改动内容（文件:行）+ 复现测试先红后绿 + 回归测试结果；
  复现测试不可行时：原因 + 替代验证及结果]
影响面：[同模式代码点、受影响的调用方、快速通道条目（如有）]

## 规格影响判定（必填）
- 是否暴露规格缺陷：是/否
- 是 → 走 内部接口-4 缺陷类回流（快速通道修复 + follow-up 规格变更单）
```

报告只宣称经过验证的部分；快速通道条目未定稿时状态是 temporary-mitigation，不得宣称彻底修复。

## 与其他 skill 的接口

- learnings：正常收尾时提示记一条 learning（一句话 + 证据链接；允许显式说"无收获"跳过——跳过要出口，不沉默略过）。

- plan-execution（互斥规则 1）：调试场景禁用 plan-execution，根因未定位前任何修复代码不得提交（T-M4-1）。调试闭环（报告产出、修复验证）之后，后续工作回路由表重新判定。
- tdd / 内部接口-5：复现测试的红绿循环与证据格式由 tdd 承载——本 skill 定义务（修复前必须先红），tdd 定方法与证据生产。
- spec-gate（内部接口-3）：hotfix 三分类判定命中后，编码前向 spec-gate ledger 登记最小记录；判定标准唯一来源在本 skill，台账与超期跟踪在 spec-gate。
- spec-gate（内部接口-4）：DEBUG REPORT「规格影响判定」为"是"时走缺陷类回流——代码先修（可叠加快速通道），规格随后补（follow-up 规格变更单）。
- code-discipline：修复 diff 的"改多少"与"用什么改"以其负向清单为裁决；verification / code-review：修复后的完成判定与评审不在本 skill 内。

## 边界与禁止项

- 禁止"试一下这个修复"式无根因改动（B-M4-2）：一切修复提议以证据链闭合为前置；3-strike 之后必须停手报告，继续尝试即违规。
- DEBUG REPORT 必填节不可省略（B-M4-5）：「规格影响判定」节缺失，报告视为未完成，完成声称不成立；结论是"否"也必须显式填写。
- 禁止在快速通道三分类之外自定义新豁免类别（B-M4-4）。
- 本 skill 不承载：测试写法与证据格式（tdd、内部接口-5）、完成判定（verification / code-review）、台账维护（spec-gate）、编码期 diff 纪律（code-discipline）。
