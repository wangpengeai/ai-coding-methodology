# brainstorming：需求澄清与方案设计（场景 B 唯一入口）

把"要做什么"已经清楚、"怎么做"还没定的任务，通过对话澄清成一份获批准的设计。批准门是本 skill 的心脏：未获用户明确批准，什么都不实现。

## 适用场景

- 任务对象已明确，方案未定：新功能怎么设计、这个需求该怎么解、改动走哪条路线。
- 上游：idea-review 结论为"值得做"的想法在此进入方案细化。
- 与 idea-review 的分界是"是否已有明确需求"；该判定由 workflow 路由表唯一做出，本 skill 不自定义进入条件。
- 入口自检（对齐路由表行 1/2 分界，2026-09-12 实测误判的教训）：任务属新方向（新插件/新产品/方法论级新能力）且未经 idea-review 三态结论时，停下提示先回路由表走 idea-review；用户显式要求跳过时，在对话中记录豁免与理由后再继续，不得静默跳过。
- 三档分级决定流程重量：Spike 产出答案，Bounded 产出对话级短设计，Architectural 产出对话级设计决策并移交规格落盘。

## 流程

### 第 0 步：动手前纪律（先于一切分级）

在给出任何方案之前：

- **显式声明假设**：把默认当真的前提写出来给用户看；拿不准就问。
- **歧义时列解释**：一段需求能读出两种以上含义时，把每种解释摆出来让用户挑，不静默选一种。
- **不静默猜测**：宁可停一拍提问，不猜着往下走；有困惑就点名说出来。
- **有更简单的做法就说**：认为存在更省的路径时直说并给理由；该反对时反对。

其余经典原则的归位：目标驱动式执行归 tdd，外科手术式修改与极简实现归 code-discipline；本 skill 只承载"动手前"这一条。

### 第 1 步：分级并宣布

先分级，再向用户说出结论与理由，让用户能够推翻：

- **Spike（可行性探针）**：要回答的是"能不能成/可不可能"，产出是一个答案，不是要保留的代码。
- **Bounded（有界变更）**：改的是本仓库里已经存在的流程，范围一圈数得过来（一个开关、一个端点、一个文件级修复）。判断标准是仓库里有没有现成流程可改——没有的，不是 Bounded。
- **Architectural（架构级）**：新项目、新子系统、重组组件装配方式、改动他人依赖的接口。

拿不准时取重的一档。棘轮单向：任务中途暴露隐藏复杂度，立即停下宣布升级，重走该档流程；任何情况不降级。

### 第 2 步：按档执行

**Spike**

1. 勘察项目上下文，够框住探针即可；按任务域检索 `内部规格`（或项目声明的权威台账）相关未决项并显式处置——义务全文在 内部接口-8 §7.1，只做指针不转述判据（内部规则-8，内部决策-049）。
2. 用两三句话说明：要回答的问题 + 打算怎么试。
3. 过批准门（一个明确的点头即可）。
4. 批准后本 skill 只定义探针问题与处置预期；真实探针执行不在本 skill 内进行——标准项目回路由表进 plan-execution（探针脚本作为计划首步），探路模式项目命中 spike-run 行；Safety Floor（禁生产凭据/数据、不可逆副作用）对探针同样生效（内部决策-008）。
5. 报告结论与建议；过程中写下的任何代码都标注为一次性，不并入主干。探针代码想保留，就是一个新任务——重新分级、重新过门。

**Bounded**

1. 勘察项目上下文：相关文件、文档、近期提交；按任务域检索 `内部规格`（或项目声明的权威台账）相关未决项并显式处置——义务全文在 内部接口-8 §7.1，只做指针不转述判据（内部规则-8，内部决策-049）。
2. 执行动手前纪律；一次只问一题，只问要紧的。
3. 在对话里给出短设计：做法、会动到的文件、怎么验证。
4. 过批准门：停下等明确的同意。
5. 批准后按路由表流转；本 skill 不自行开始实现。

**Architectural**

1. 勘察项目上下文；按任务域检索 `内部规格`（或项目声明的权威台账）相关未决项并显式处置——义务全文在 内部接口-8 §7.1，只做指针不转述判据（内部规则-8，内部决策-049）。
2. 执行动手前纪律；一次一题，弄清目的、约束、成功标准。若任务实际是多个独立子系统的集合，先帮用户拆分成可独立交付的子任务，再对第一个子任务走全流程。
3. 给出 2-3 个实质不同的方案，含取舍与推荐。
4. 分节呈现设计（架构、组件、数据流、错误处理、测试面），每节征求确认；每节长短随复杂度伸缩，不硬凑篇幅。
5. 过批准门：整份设计获明确批准。
6. 移交设计决策落盘（见"与其他 skill 的接口"）。
7. 之后进入计划通道（plan-writing）。

### 批准门（三档共用）

- 未获用户明确批准：不写任何代码、不调用任何实现类技能、不搭任何脚手架。
- 门不随任务简单度缩水：简单改变的是设计文本的长度（可以短到两三句），永远不改变"先摆出来、获批、再动手"这个顺序。恰恰是"简单"任务里，未经检验的假设浪费的工作最多。
- 批准必须显式：把打算做的事摆出来，停下等答复；把方案陈述与开始实现连在同一口气里，就是绕门。
- 过门之前形成的决策只是候选决策，不得移交落盘——规格侧对未过门的移交一律拒收。

### 反合理化对照

| 念头 | 现实 |
|---|---|
| "太简单，不用过门" | 简单意味着设计只有两三句，不意味着免批准。 |
| "挑个轻的档省事" | 为省事而降档本身就是疑点；取重的一档。 |
| "设计显然成立，边看边做" | 门是"批准"这个动作，不是设计的篇幅。 |
| "我熟这类应用，算 Bounded" | Bounded 量的是仓库，不是熟悉度；新项目没有现成流程，就是 Architectural。 |
| "探针能跑，代码就留着" | 探针的产出是答案；保留代码是新任务，重新分级过门。 |
| "变复杂了，但快做完，不重分级了" | 隐藏复杂度触发升级，停下宣布。 |
| "探针批过，后续变更跟着批" | 每个任务独立分级、独立过门。 |

## 与其他 skill 的接口

- learnings：正常收尾时提示记一条 learning（一句话 + 证据链接；允许显式说"无收获"跳过——跳过要出口，不沉默略过）。

- 上游：idea-review（结论"值得做"交接至此）；路由表把"任务已明确、方案未定"的唯一入口指到本 skill。
- **Architectural 移交（内部接口-6）**：批准门通过的设计决策（背景、选项、裁决、理由）移交 spec-gate 的 spec-writing，落盘为 `.sdd/` 下的设计决策条目。本 skill 只产出对话级决策记录；workflow 任何 skill 不得自行落盘规格文档。未过批准门的决策移交过去，规格侧必须拒收。
- 下游：plan-writing（设计决策要落成计划时）；实现入口由路由表唯一判定（计划已批准才进执行），本 skill 不直接启动实现。
- 跨会话未决项：按 内部接口-8 登记 OPEN-n，不写自由文本待办标记。

## 边界与禁止项

- 禁止私写规格文档：设计决策落盘的唯一通道是上面的移交；对话记录不是规格。
- 未过批准门：不得实现、不得移交——这是双向约束。
- 禁止跳过分级直接给方案；分级宣布在先，用户可推翻。
- 本 skill 不承载编码期纪律（改多少与用什么改归 code-discipline）与验证纪律（怎么验证归 tdd 与 verification）。
- 会话即媒介：澄清、方案与设计全部以对话完成，不引入额外的工具流程。
