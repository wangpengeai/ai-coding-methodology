# plan-execution：计划执行（"计划已批准"唯一实现入口）

把通过评审的计划逐条落地为代码。三种执行模式共享同一副骨架——计划加载、逐条执行、检查点、收尾——差异只在派发方式；选择哪种模式不改变任何前置条件与执行纪律。

## 适用场景

- 用户状态命中路由表"计划已批准"行：评审通过的计划在此进入实现，这是全体系唯一的实现入口。
- 三种模式按任务形态与宿主能力选择（见"模式选择"），从加载计划到最后一个任务完成，全程在本 skill 内进行。
- 不适用的场合一律由路由表判定：计划未评审归 plan-review；报缺陷/异常/回归归 root-cause-debugging（互斥规则 1）；本 skill 不自行改道，也不受理绕行请求。

## 前置条件

三条全部满足才开工。任何一条不满足，停下退回对应入口处理，不在本 skill 内变通。

### 一、计划已过 plan-review

- 执行的唯一凭据是计划已通过评审；未评审或评审未通过的计划一律拒绝执行（B-M4-1）。
- 机械凭据（内部规则-10，内部决策-007）：声明 plan-execution 必须显式点名计划——
  `node <插件根>/hooks/routing-declare.mjs plan-execution --lease <本轮leaseId> --task-id <任务号> --plan docs/plans/<计划名>.md`；
  凭据校验只认该计划当前哈希的 v2/v3 sidecar（taskId/planPath/planSha256 + reviewMode/reviewInstances/reviewReason 一致 +「结论：通过」；v2 仅 self/ratified 历史可读；独立/mixed 须 v3 另加 `reviewRound` + `reviewProvenance`，内部任务-191），仓库中其他通过记录不构成凭据，旧 sidecar 仅历史可读、须重审或按 D9 原位补 v3 字段（同轮以新校验器验证，防自锁）。
- 拒绝就是拒绝：明说"计划未过评审，先走 plan-review"，不在执行中边做边补评审，也不替用户"先看看计划顺手开工"。
- 本 skill 不复评计划：执行中发现计划或设计有误的处置见"与其他 skill 的接口"，不是回头自己改计划。

### 二、`.sdd/` 项目先过适用性判定矩阵

- 项目存在 `.sdd/` 体系（`内部治理状态` 存在）时，开工前先过 spec-gate 的适用性判定矩阵（内部接口-2），按判定结论（required/lightweight/exempt 等）确定本次执行背负的规格义务。
- 判定依据不足时按 lightweight 处理并注明理由，不得静默升级；项目未接入 `.sdd/` 体系时跳过判定，不报错。
- 判定结论带入执行全程：后续的任务验证与完成声称都按该结论执行；判定本身的细节归 spec-gate 侧，本 skill 只负责触发与遵守。

### 三、隔离工作区

实现工作必须发生在隔离环境；未经用户明确同意，不得直接在主分支开工。按以下顺序落实：

1. 先探测现状：当前已在独立分支或工作树内就直接使用，不重复创建。
2. 宿主原生工具优先：宿主提供分支/工作树类工具时用它——目录选址、分支创建与清理由工具自管；绕开原生工具手工建目录，会留下宿主看不见也管不了的孤儿状态。
3. git 工作树兜底：确无原生工具时用 git worktree 手工创建，工作树目录必须已在版本库忽略清单内，防止工作区内容被整棵误提交。
4. 基线验证：开工前运行一遍项目测试确认起点干净。基线是脏的，之后每一次失败都无法归因——报告失败并问用户是否先处置，不带病开工。

### 四、计划豁免语义锚定（内部决策-067）

- `--exempt` 必须逐字引用用户针对计划/评审流程本身的明确表态，并给 `--exempt-scope plan|review`：`plan`＝豁免计划编写与评审（禁 `--plan`）；`review`＝仅豁免评审（`--plan` 必须存在且正文含 `豁免引文：` 行）。
- 目标/推进指令（「继续」「先处理 X 再处理 Y」「逐项修复」）不构成流程豁免；被拒时回用户要流程原话，不得改写为用户未说过的引文。
- 执行中不得把豁免当成跳过计划/评审的通用许可；完成侧 gate `exemptAnchor` 会对无计划锚的 v2 豁免阻断。误声明退役须用户显式 `--exempt-revoke` + 撤销原话 + 已评审计划。

## 流程

先定模式，再按所选模式走完共享骨架：**计划加载 → 逐条执行 → 检查点 → 收尾**。

收尾含一项共用义务指针（内部决策-039）：全部任务完成、按路由表流转前，检查任务过程文件中登记的未决项——它们必须在分支收尾移交到项目声明的权威台账；义务全文唯一载体在 branch-finishing「未决项移交义务」，本条只做指针、不转述判据。
- 收尾含 learnings 沉淀：写入时点＝verification 签发前（冻结前）；两出口与条目格式归 learnings skill，本条只做指针。

### 模式选择

| 判定 | 选择 |
|---|---|
| 宿主无子代理能力，或任务强耦合、需要全程同一上下文 | 模式 A 顺序执行 |
| 宿主有子代理能力，任务基本独立 | 模式 B 子代理派发（逐个串行派发） |
| 存在两个及以上无共享状态的独立任务 | 这些任务走模式 C 并行；其余任务照旧串行 |

拿不准时选串行。并行是省时间的优化项，不是默认项；串行永远不输正确性。

### 模式 A：顺序执行

当前会话自己逐条执行，每个任务完成当场验证。

- **计划加载**：通读计划一遍，记住全局约束与任务顺序；每个任务记一条待办。对计划有疑虑先向用户提出，不带疑虑开工。
- **逐条执行**：按计划顺序一次一个任务，照计划步骤做，不跳步、不加戏、不自行改道；每一步完成即运行计划指定的验证，验证不过不进入下一步。改动范围多大由 code-discipline 约束。
- **检查点**：每个任务收口时对照该任务的验收标准自查一遍（该做的都做了？没做多余的？验证证据在？），通过才标记完成并进入下一任务。
- **收尾**：全部任务完成后按路由表流转，本 skill 到最后一个任务完成为止（见"与其他 skill 的接口"下游）。

停机条件：遇到阻塞（依赖缺失、验证反复失败、指令读不懂）立即停下问用户，不猜着继续，不硬闯。

### 模式 B：子代理派发

每个任务派发实现者子代理（复用优先，见下），主会话只做调度、供上下文与评审，不亲自写实现。

- **计划加载**：同模式 A；另做一次开工前通扫——找计划内部冲突（任务相互矛盾、步骤与全局约束打架、计划要求与验收标准脱节），发现先裁决并记录，再派发第一个任务。
- **逐条执行**（每任务一循环）：
  1. 写自包含任务简报：任务全文、该任务在项目里的位置、前序任务产出的接口与决策、全局约束、报告要求。简报是需求的唯一载体，精确值（数字、签名、用例）只写在简报里；不让子代理去读整个计划文件。
  2. 派发实现者（复用优先，按元技能「代理实例复用与再水化」的探测程序）：先列可寻址实例清单（有桥接清单先列它）并查实例台账——存在可续实现者（同链优先）→ 经续聊入口回派复用；否则派发 fresh 实现者并做完整交接（任务简报 + 上轮报告 + 意见清单 + 实例台账登记）。有桥接清单时优先普通子代理通道；持久成员通道留作任务协同/加速（按需最小使用，默认 ≤1 名/批，除非用户显式要求）。fresh 实现者不继承主会话的上下文与历史；子代理内禁止再派发子代理。简报必须点名随行纪律（code-discipline、tdd）与对应语言规范要点。
  3. 任务级评审后放行：实现者报告完成后，对照简报核验收（要求全做了？没做超范围的？）并查质量，通过才放行下一任务；不过就回派同一实现者修正（可续则复用原实例；不可续则 fresh+完整交接并按元技能全局规则登记为再水化；台账记录），修正轮次设上限，超限停下逐条裁决，处置记录在案，不静默丢弃任何一条意见。
- **检查点**：每任务完成记一行进度台账（任务号、结论、提交范围）。会话压缩后凭台账与版本历史恢复进度，不凭记忆；已完成的任务不得重复派发，从第一个无完成记录的任务续起。
- **收尾**：所有任务完成后做一次全分支范围终审（一次派发、一份完整清单，不按意见逐条各派一个），终审处置同任务级评审规则；然后同共享骨架收尾。

连续执行纪律：任务之间不停下来向用户请示或汇报进度。仅以下四种情况中断等待用户，其余的冲突、歧义与额度问题自行裁决并记录在案：

1. 不可逆或破坏性操作；
2. 安全敏感动作；
3. 超出本工作区的副作用——合并、推送共享分支、发布这类该先问的动作；
4. 计划烂到每条前进路线都只能靠猜。

裁决要落记录：裁了什么、依据什么、错了代价是什么。用户没点头不等于没交代。

### 模式 C：并行派发

把无共享状态的独立任务同时派出，其余任务照常串行。每个并行任务一个独立实现者并登记实例台账；批内不得复用同一实例（批内独立＝互不复用；跨批按全局规则复用，共享状态禁令不变）。

- **并行准入（唯一标准）**：两个及以上任务互不依赖、无共享状态——改的是不同文件或不同子系统，谁也不读写对方的产物。凡共享状态（同文件、同接口、同资源）的任务必须串行；不能证明独立，就按不独立处理。
- **计划加载**：同共享骨架；另做显式分组：哪些任务可并行、哪些必须串行及先后顺序，分组结论先落待办再开工。
- **逐条执行**：每个并行任务一个独立子代理，简报按模式 B 的自包含标准，另加一条硬约束——只许改本任务范围内的代码。并行批全部返回之前，不启动依赖它们的后序任务。
- **检查点（并行批收口三查）**：逐个核对返回结果与简报的符合性；查各任务改动是否冲突（同文件碰撞、接口断裂）；运行完整测试套件确认合并后整体成立。任一查出问题，停下处置完再走，不带病进入下一批。
- **收尾**：同共享骨架。

### 执行期随行纪律（引用，不展开）

- code-discipline：管"改多少"与"用什么改"——每个任务里哪些能改、哪些是顺手重构禁令、源码改动一律走编辑工具，以它为准。
- doc-discipline：管"文档与注释写什么、谁负责保持同步"——写/改代码或归档文档时七条款生效，以它为准。
- tdd：管"怎么验证"——任务内测试先行与验证纪律，以它为准。

三条对主会话与一切子代理同等生效；三种模式的任务简报与自查都必须把它们点名带上。

### 长任务阶段复审（漂移三级处置）

长任务（多任务、跨会话）在阶段性目标达成后必须主动复审：对照计划验收行自查实现漂移，需要时发起 code-review；不等收尾才发现偏航。发现漂移按「计划文档被批准的字需要改吗」分三级处置，不统一回炉：

1. **计划未破 → 就地纠偏**：漂移只在计划未固定、明确留给实现自由的层面（函数选择、文件组织、等价实现路径、小重构），纠正后仍逐条通过计划验收行，任务边界、设计决策、specRefs 均未动——对齐回计划继续执行，进度台账记一行（漂移现象 + 纠正动作），不回炉不重审。
2. **计划破了 → 回炉重审**：验收行要改写才能保持为真、任务边界扩张或收缩、计划绑定的设计决策/specRefs 变了、计划路线被证不可行（任一即破）——回 plan-writing 修订计划，修完重走 plan-review 再回来；重审按 delta（重审标注取代既有记录），成本与改动成比例，不是全量重审。
3. **规格错了 → 规格回流**：漂移的根因是规格本身有误或歧义，计划只是忠实执行了坏规格——走 spec-gate 的 spec-writing 回写规格（内部接口-4），回 plan-writing 修不出正确结果。

- **架构事实记录义务（内部决策-052/内部模块-20 内部规则-6）**：阶段复审与收尾时，将架构级事实追加到被治理项目 `.context/architecture-feedback.jsonl`（义务全文唯一载体在 内部模块-20 内部规则-6；本 skill 只做指针、不转述判据）。

## 与其他 skill 的接口

- learnings：正常收尾记一条 learning（一句话＋证据链接）；两出口与冻结时点归 learnings skill（写入时点＝verification 签发前）。

- 上游：plan-review（评审通过的计划交接至此）；`.sdd/` 体系下先过适用性判定矩阵（内部接口-2，见前置条件二）。
- 执行中发现设计有误：停下执行，回 plan-writing 修订计划，修完重走评审再回来；错误出在规格层的，先经 spec-gate 的 spec-writing 回写规格、保持设计与实现一致——本插件 skill 不自写 `.sdd/` 下任何文档。
- 调试任务禁入（互斥规则 1）：报缺陷/异常/回归的用户状态由路由表命中 root-cause-debugging 行，不会也不应进入本 skill；执行途中需要转入调试场景时，回到路由表重新判定，不在本 skill 内改道。
- 随行引用：code-discipline（改多少 + 用什么改）、doc-discipline（文档与注释写什么）、tdd（怎么验证）——见"执行期随行纪律"。
- 下游：全部任务完成后按路由表进入 verification（证据先运行）→ code-review，分支收尾归 branch-finishing；本 skill 的职责到"最后一个任务完成"为止。

## 边界与禁止项

- 不评审计划本身：计划好不好归 plan-review；B-M4-1——禁止在未评审计划上运行，发现即拒绝并退回。
- 不收尾分支：合并、清理、去向选项呈现归 branch-finishing。
- 不自定义进入条件与改道：入口判定归 workflow 路由表；场景切换回表重判，本 skill 与其他入口 skill 之间不互相改道。
- 不落盘规格：`.sdd/` 与规格文档一律归 spec-gate（内部接口-6 与全局规则）；执行进度台账、任务简报是项目内轻量资产，不进规格受检文档集。
- 不写自由文本待办标记：跨会话未决事项的唯一合法形态是 spec-gate 的 OPEN-n 结构化未决项（内部接口-8）。
- 并行禁令：共享状态任务不得并行；不能证明无共享状态即视为有。
- 子代理两条禁令：实现者子代理不得再派发子代理；模式 B/C 下主会话不亲自改实现——主会话的改动不经任务级评审，发现的问题一律回派。
- 复用纪律：主会话不得以台账记录替代实际的复用尝试/不可用证据（台账是记录，不是复用的替代品；不可用三态须有宿主错误或检索记录，见元技能全局规则「代理实例复用与再水化」）。有桥接清单而不用普通子代理通道、或不留清单检索记录即新发，同属「以台账记录替代实际的复用尝试」（本批禁用）。
