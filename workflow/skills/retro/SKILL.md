# retro：周期回顾（指标解读 + 证据锚定 + 快照趋势）

对一个周期内的 git 提交历史做定量回顾：跑指标、带着局限解读、产出锚定到具体提交的结论与行动项、把快照存进项目并与上次对比。核心纪律只有一条（B-M6-4）：每条评价必须证据锚定——没有提交哈希/文件/日期支撑的表扬或批评不许写。

## 适用场景

- 路由表"周期节点"行：用户显式说"做一次回顾/复盘"，或到达周期节点（每周收工、迭代结束等）。
- 单仓库维度：只回顾当前项目仓库的 git 历史；跨仓库全局聚合不在本插件范围（见边界）。
- 前提：仓库存在且可读。指标脚本对零提交仓库返回全 0，此时如实报告"本周期无提交数据"，不硬凑结论。

## 流程

### 第 1 步：跑指标

```bash
node workflow/scripts/retro-metrics.mjs <repoPath> [--since <ISO|日期>] [--until <ISO|日期>] [--base <ref|hash>]
```

- 成功：stdout 输出一个 JSON——`{ weightedCommits, sessions, fixRatio, focusScore, selfCheckHeat, generatedAt, period }`；`period` 三态说明统计范围（`{range:'bounded'|'full-history', since, until, base}`）。
- 周期口径（内部规则-8）：回顾"本周期"必须传 `--since/--until`（或 `--base` 基线）；**`full-history` 输出不得冒充本周期结论**——解读时显式说明范围与口径差异。
- 失败（退出码 1，`error` 字段说明原因）：非 git 仓库等环境问题——如实告知用户并终止，禁止编造或凭印象估算指标值。

### 第 2 步：指标解读（含义与局限一起说）

| 指标 | 含义 | 局限（解读时必须带上） |
|---|---|---|
| weightedCommits | 按改动规模加权的提交得分（单提交 = 文件数 × 增删行数，上限 20） | 大不等于重要：批量格式化、依赖整包引入会虚高；得分低也不等于没干活 |
| sessions | 相邻提交间隔严格大于 45 分钟切分出的会话数 | 提交时间不等于编码时间；攒批提交的习惯会压低会话数 |
| fixRatio | 主题匹配修复类关键词（fix/修复/resolve）的提交占比 | 关键词匹配有误报漏报；偏高是"评审缺口"的方向信号，不是定论 |
| focusScore | 改动最集中的顶层目录在全部文件改动中的占比 | 高=聚焦、低=分散只是启发式；跨目录重构天然分散，不都是坏事 |
| selfCheckHeat（内部模块-15/内部决策-019） | 自察异常热度：`内部工作流状态` 的 open 计数 + 30 天 digest 聚合 Top3；v2 加法键 `causeCounts`（窗内按 cause 分组）/`dispositionRate`（窗内非证据面处置率）/`oldestPendingAgeDays`（最老待排查）/`lostFacts`（兜底旁路非空行数） | 仅本项目根运行态口径（跨机/跨开发者不可比）；榜首 digest 是"该排查什么"的方向信号，需回 incident-cli list 对照原始记录；v2 四键同属启发式（处置率分母只覆盖窗内非证据面），不得当 SLA/考核结论 |

指标只提供方向。任何落到人/落到事的判断，都必须由第 3 步的证据来支撑。

### 第 3 步：证据锚定语气规则（B-M6-4）

每条做得好（praise）/ 待改进（growth）评价，必须引用具体锚点：提交短哈希、文件路径、日期——至少其一，且出处真实可查（当期 `git log`/`git diff` 现场核对）。

- 合格：「`a1b2c3d`（09-08）把登录模块拆成三个可独立回滚的小提交合入——这周做得最好的一件事。」
- 不合格：「这周整体质量不错，继续保持。」

同一规则约束批评：不写"测试覆盖不足"这种无锚定判断，要写「本周 14 个提交无一个新增测试，且 `b3f4e5d` 起是一条连续修复链——修复没有测试兜底」。

- 禁止凭印象编造哈希、路径或日期：锚点错误比没有锚点更糟，一次被证伪的锚点会让整个回顾失去信任。
- 语气上，改进建议按"值得投入"来表述（为什么值得做），不按"你失败了"来表述。

### 第 4 步：结论与行动项

- 结论分两栏：做得好（1-3 条，各带锚点）、值得改进（1-3 条，各带锚点）；没有素材就如实写"本周期无"，不凑数。
- 每条行动项落到唯一去处：可复用的经验教训 → learnings 记一句话；需要跨会话跟踪的事项 → spec-gate 的 OPEN-n 结构化未决项；两者都不是的，它就不该是行动项。禁止把行动项散落成自由文本标记。
- 行动项要小而具体：下个周期可执行、可验证；不写"提高质量意识"这类无法验收的口号。

### 第 5 步：快照与趋势对比

- 快照存项目内 `.context/retros/<date>.json`（如 `.context/retros/2026-09-12.json`；同日多次回顾追加序号 `-1`、`-2`）。内容至少含：`date`、第 1 步的指标 JSON、第 4 步结论与行动项摘要。
- 写入前先取上一份快照（同目录按文件名排序取最新一个）：有 → 在报告里输出"趋势对比"小节（四项指标 上次 → 本次 及增减方向，配一句话解读，注明对比的是哪一天）；没有 → 注明"首次记录，下次回顾起可见趋势"。
- 快照是给下一个周期读的机器可读留痕：独立的 JSON 文件，项目内路径，不与任何插件私有日志格式挂钩。

## 与其他 skill 的接口

- 上游：路由表"周期节点"行（`retro`/`health`/`learnings` 并列，用户显式触发或周期提醒）；无前置 skill 依赖，可与 health 同期各自运行。
- learnings：第 4 步行动项的一处落地（一句话经验）；回顾解读时也可引用既有 learnings 作参考（如有）。
- spec-gate：需跟踪事项以 OPEN-n 登记；本 skill 不写 `.sdd/` 下任何文档（B-M6-1 反向边界）。

## 边界与禁止项

- 只读 git 历史：除 `.context/retros/` 快照外不写任何文件，绝不改代码与文档（内部规则-2 边界）。
- 全局跨仓库模式不移植：跨仓库聚合依赖全局数据目录，本插件不引入；要回顾哪个仓库，就进哪个仓库运行。
- 禁止无锚定评价与编造锚点（B-M6-4）：这是本 skill 的存在理由，违者该次回顾作废重做。
- 指标不是考核：输出用于过程改进，不用于绩效表述；单人仓库同样适用（回顾是给自己的，不设"团队分解"环节）。
