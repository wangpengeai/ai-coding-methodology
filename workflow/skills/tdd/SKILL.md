# tdd：测试驱动执行纪律（执行期随行）

铁律：没有先行的失败测试，就没有实现代码。本 skill 用红-绿-重构循环承载这条纪律，动手前先把任务转译成可验证的成功标准，循环中产出的 RED/GREEN 证据按 内部接口-5 格式落盘。

## 适用场景

- 随行 skill，不是入口：不开场、不路由，跟随一切"新增行为或修 bug"的实现场合——计划执行中、缺陷修复中、评审返工中；由所属场景的入口 skill（plan-execution 等）按需引用。
- 适用与否不由本 skill 判定：TDD 适用性结论（strict / characterization-first / exempt）来自 spec-gate 判定矩阵（内部接口-2），经 plan-execution 前置消费；本 skill 承载前两者的执行纪律，exempt 走豁免记录（见接口节）。
- 遗留代码无测试覆盖时（characterization-first）：先写特征测试锁定现状——特征测试全绿是基线，之后的改动照常走红-绿-重构。
- 前提（内部验收-1）：项目有可用测试设施（框架与运行命令），或可在本任务内建立；失效时的处置见边界——搭测试骨架是第一步。
- 原则归位：目标驱动（Goal-Driven）由本 skill 承载（"先想后写"在 brainstorming，外科手术式修改与极简实现在 code-discipline）；单源无副本，各 skill 正文互不重复。

## 流程

### 第 0 步：可验证成功标准（动手前）

把祈使式任务转译为可验证目标——说不清"做成了会看到什么"，就不动手：

| 祈使式任务 | 转译后的可验证目标 |
|---|---|
| "修复 X" | 先写一个复现 X 的失败测试，再让它通过 |
| "给表单加校验" | 先写非法输入被拒的失败测试，再让它通过 |
| "重构 X" | 相关测试在重构前后保持全绿 |

- 多步任务逐步转译：每一步写明"做什么 → 用什么验证"，验证不过就不算做完。
- 目标不可验证时回 plan-writing 明确验收标准，不带模糊目标进实现——否则"验证"会退化成"看起来能跑"。
- 强的成功标准让执行可以自驱循环：循环到验证通过为止，而不是循环到感觉良好为止。

### 第 1 步：红-绿-重构

**RED：先写最小失败测试**

- 一个测试只测一个行为，名字说清被测的行为，不写"测试1"这类名字。
- 尽量测真实代码；mock 只在无法避免时使用。
- 运行并亲眼看到失败——没看过失败就不算数：没看过失败，就无法证明这个测试真能抓住目标问题。
- 确认失败原因正确：失败必须来自"行为还不存在"（断言不通过，或预期中的编译缺口——RULE-TDD-002 的分类门）；失败来自测试自身缺陷或环境故障时，先修它们再重跑，直到以正确的原因失败。
- 测试一写就通过：说明测到的是既有行为，该改的是测试，不是接着写实现。
- 落 RED 证据（第 2 步格式）；RED 证据必须先于实现代码存在（T-M4-3）。

**GREEN：最小实现**

- 写恰好让测试通过的实现：不加测试之外的功能、不做顺手重构、不做"顺便改进"。
- 用与 RED 相同的测试选择集运行（RULE-TDD-003）：目标测试变绿，受影响的既有测试保持绿；选择集变了就要解释原因并针对最终测试重建有效 RED。
- GREEN 失败时修实现，不改测试。
- 落 GREEN 证据。

**REFACTOR：全绿之下清理**

- 只在全绿之后做：去重、改名、提取公共函数；不加任何新行为。
- 清理期间保持全绿，并跑受影响的回归测试确认（RULE-TDD-004）。
- 测试难写是设计信号：难测往往因为难用，先简化设计（如引入注入缝），不硬测。

**反合理化表**

| 念头 | 反驳 |
|---|---|
| "这个改动太简单，不用先写测试" | 简单的代码一样会坏，而测试只要几十秒；"简单"改变的是测试的长度，不是要不要写测试。 |
| "先写实现再补测试，效果一样" | 后补的测试一跑就绿——你从没看过它失败，它可能测的根本不是你以为的东西。先写测试是定义"该做什么"，后补测试只是描述"已经做了什么"。 |
| "手动验证过了" | 手动验证无法复跑、没有覆盖记录、换人就丢边界情况；它是一次抽查，不是证据。 |
| "测试环境没搭好，先跳过" | 测试设施是前置不是可选项——搭最小测试骨架就是第一步（见边界）；真不可行走豁免记录，不静默跳过。 |
| "测试太难写，硬着头皮写完就行" | 难写的测试在报告设计耦合；先解依赖再测，硬测出来的测试同样脆弱。 |

### 第 2 步：证据格式（内部接口-5）

本 skill 是证据生产方，格式契约的唯一来源是 内部接口-5：

- RED 与 GREEN 各记一条证据，五要素：命令、工作目录、退出码、输出摘要、关联（RULE-TDD 编号或 specId）。
- 前置：验证命令真实运行过，禁止凭记忆补录；退出码缺失或伪造，证据即无效（blocking）。
- 敏感信息写入前脱敏（沿用 spec-gate capture 的脱敏规则）。
- 关联缺省时消费方按契约报 warning（证据未关联规则或规格），因此每条必填：RED 证据关联 RULE-TDD-001，GREEN 证据关联 RULE-TDD-003（同一选择集）；对应规格条目时关联 specId。
- 落点：项目有 `.sdd/` 体系（`内部治理状态` 存在）时，经 `/spec-gate:evidence -- <cmd>` 捕获，或按格式直接写入 `evidence.jsonl`；未接入 `.sdd/` 时按同一格式记入任务记录，供 verification 复用。

最小 JSON 行示例（RED 一条；GREEN 同构——退出码 0、摘要为通过）：

```json
{"command":"npm test -- tests/retry.test.ts","workingDirectory":"D:/repo","selectionCriteria":"tests/retry.test.ts","exitCode":1,"executedAt":"2026-09-12T10:30:00+08:00","keyOutputSummary":"1 failed：期望重试 3 次实际 1 次（断言失败，行为缺失）","relatedRule":"RULE-TDD-001"}
```

字段沿用 spec-gate 的 command-evidence schema（命令/工作目录/选择条件/退出码/执行时间/输出摘要），关联字段（relatedRule/relatedSpec）是 内部接口-5 在其上的扩展。

## 与其他 skill 的接口

- code-discipline：分工声明——本 skill 管"怎么验证"（何时写测试、怎么算通过、证据长什么样），code-discipline 管"改多少"（diff 范围与实现体量）与"用什么改"（源码改动一律编辑工具，脚本批量替换禁入）。GREEN 的"最小实现"由两者共同约束：tdd 说"恰好让测试过"，code-discipline 说"不越任务边界"；执行期并行生效、互不取代。
- verification：证据复用——执行期落盘的 RED/GREEN 证据按 内部接口-5 可被 verification 直接引用，完成前验证不重复生产；"完成声称"的聚合判定归 verification（互斥规则 2 的裁决不在本 skill）。
- root-cause-debugging：修 bug 衔接——根因定位后进入修复，先写最小复现测试作为该缺陷的 RED，再走红-绿-重构；复现测试现实不可行时，记录原因与替代验证（RULE-TDD-005 语义：豁免须记授权、原因、替代验证与剩余风险，未记录默认阻塞），不得静默跳过。
- plan-writing：上游——第 0 步发现目标不可验证时回流补验收标准；本 skill 不自行扩写验收。

## 边界与禁止项

- 不覆盖测试策略选型：选什么框架、测试如何分层组织、覆盖率目标，均不在本 skill 范围。
- 无测试设施时（前提 内部验收-1 失效）：搭最小测试骨架是第一步，不是跳过测试的理由；骨架本身也取"恰好能跑第一个测试"的最小形态。
- **B-M4-3**：禁止先写实现后补测试并声称 RED——没有 RED 证据即违反本条；先写的实现不豁免，删除后从测试重新开始，不把它留在手边当底稿继续改。
- 豁免不归本 skill 定义：测试不可行的豁免记录归 spec-gate（RULE-TDD-005），本 skill 只负责触发与如实上报，不私设豁免类别。
- 本 skill 不定义进入条件：场景判定归路由表，执行入口与判定矩阵消费归 plan-execution（内部接口-2）；本 skill 是被引用的随行纪律，不是第二个判定源。
